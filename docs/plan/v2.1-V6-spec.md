## 0. Decisions

- **X-37 — Client-side rate limiting.** review-mcp keeps its own model calls within a configured number of requests per minute, per endpoint, shared by every tool call of the process (parallel focused reviews included). HTTP 429 puts the whole endpoint into a cool-down, so concurrent callers wait together instead of each retrying into the limit. Waiting is bounded and reported.
- **X-38 — Fallback model chain.** Up to three fallback models, tried in order when a model call cannot be served by the current model. The run stays on the model it fell back to.

**Owner defaults (approved 2026-10-15):**
1. Scope of the limiter: **one process** (one MCP client session). A machine-wide limiter across processes is backlog.
2. A 429 with a fallback configured: **wait first, then fall back.** Wait while the needed wait is at most `llm.max_rate_wait_seconds`; when it is longer, or the rate-limit retries are used up, move to the next model.

**Architect defaults (approved by the owner 2026-10-15):**
3. `llm.requests_per_minute` defaults to **0 (no client limit)**, so nothing changes for users who set nothing; the docs recommend setting it to the gateway's limit.
4. `llm.max_concurrent_requests` defaults to **0 (unlimited)**.
5. `llm.max_rate_wait_seconds` defaults to **60** (range 0–600); `llm.max_rate_retries` defaults to **4** (range 0–20). Rate-limit retries do not use up `llm.max_retries`.
6. The fallback chain is **sticky per run**: after a call falls back, the rest of that run starts at the fallback model.
7. A context window that does not fit a prompt makes the chain **skip** that fallback for that call. A run-level retry of preparation with a larger window (the `DoesNotFit` case of DQ-9) is backlog.

## 1. WP-8a — Housekeeping (Sonnet)

One commit per item, no behaviour change outside the item.

1. `fix(improve): tolerate tab and space differences when verifying suggestions` — a suggestion whose existing-code lines differ from the file only in leading tabs versus spaces (or trailing whitespace) is verified, as seen in the GitLab acceptance. The comparison normalises leading whitespace runs (a tab counts as the run it replaces) and trailing whitespace on both sides; the suggestion body itself is never rewritten. 4. `fix(review): say what a merged publish dropped only when the overview changed` — the note of WP-7f ("N findings listed only in the earlier overview were not carried into this publish.") is added only after the overview was edited or a replacement was posted; when neither happened, no such note. **[canary]** add the note before the publish outcome: the both-writes-failed case fails.

## 2. WP-8b — Rate limiting (Opus)

### 2.1 Configuration

| Key | Env | Type, default, range | Meaning |
|---|---|---|---|
| `llm.requests_per_minute` | `REVIEW_MCP_LLM_REQUESTS_PER_MINUTE` | int, 0, 0–100000 | Most HTTP requests (every attempt, retries included) started in any 60-second window, per endpoint. 0 = no client limit. |
| `llm.max_concurrent_requests` | `REVIEW_MCP_LLM_MAX_CONCURRENT_REQUESTS` | int, 0, 0–256 | Most requests in flight at once, per endpoint. 0 = unlimited. |
| `llm.max_rate_wait_seconds` | `REVIEW_MCP_LLM_MAX_RATE_WAIT_SECONDS` | int, 60, 0–600 | The longest one wait for the rate limit may be (a limiter slot, a cool-down or a 429's delay). A longer needed wait is not waited for (§2.3). |
| `llm.max_rate_retries` | `REVIEW_MCP_LLM_MAX_RATE_RETRIES` | int, 4, 0–20 | Retries after HTTP 429 for one model call, counted apart from `llm.max_retries`. |

`server_info` shows all four. Validation as for the other `llm.*` keys.

### 2.2 The limiter

1. **Registry.** One process-wide registry of limiters, created once (not per run: `wiring.NewLLM` stays request-scoped and looks the limiter up). Key: the normalised base URL plus an HMAC-SHA256 of the API key under a random per-process salt (empty key → empty part). The key itself is never stored, logged or compared in clear; the HMAC is not shown anywhere. Two models on the same base URL and key share one limiter (a gateway limits the key, not the model).
2. **Window.** A sliding window: the start times of the requests of the last 60 seconds. A request may start when fewer than `requests_per_minute` started in the last 60 s, no cool-down is active, and (when set) fewer than `max_concurrent_requests` are in flight. Otherwise it waits. The configuration of the first run that creates the limiter applies; a later run with other values updates the limits in place (serve mode reloads).
3. **Fairness.** Waiters are served in arrival order (FIFO), so parallel focused runs progress evenly.
4. **Waiting.** Every wait is `ctx`-aware (a canceled run stops waiting at once and gives up its place). Before waiting, the limiter computes the wait. When it exceeds `max_rate_wait_seconds`, the request does not wait: it fails with the class `rate_limited` and the internal reason `wait_too_long` (§2.3).
5. **Cool-down on 429.** A 429 sets the endpoint's cool-down to now + D, where D is, in order:
   - `Retry-After` (seconds or HTTP date), when present;
   - else the OpenAI-style header `x-ratelimit-reset-requests` (durations such as `6s`, `1m30s`, `250ms`), when present and parsable;
   - else 10 s, 20 s, 40 s… doubling per consecutive 429 of that endpoint, reset by the next success.

   D is capped at 600 s (above `max_rate_wait_seconds`, so a long reset is reported, not waited for). Every caller of that endpoint waits for the cool-down, not only the one that got the 429.
6. **Headers on success.** When a successful response carries `x-ratelimit-remaining-requests: 0` and a parsable `x-ratelimit-reset-requests`, the cool-down is set to that reset. Other header families are ignored (no guessing).
7. **Retry.** A 429 is retried after its cool-down, up to `max_rate_retries` times for that call, as long as each wait is at most `max_rate_wait_seconds`. Other retryable classes keep today's policy (`max_retries`, `backoff`, `Retry-After` capped at 30 s). The existing 30-s cap no longer applies to 429.

### 2.3 Result and messages

1. Result metadata gains `rate_limit_waits` (count) and `rate_limit_wait_ms` (total) of the run; both always set.
2. Note when the run waited at least 1 s in total: "The LLM endpoint's rate limit delayed this run by N s." (rounded).
3. When a call fails with `rate_limited` and there is no fallback left (WP-8c), the client sentence is the existing rate-limited one plus, for `wait_too_long`: "The endpoint asked for a wait longer than llm.max_rate_wait_seconds (N s)." No header values, no URL.
4. Debug log per wait: endpoint (redacted base URL), reason (`window`, `concurrency`, `cool_down`), wait in ms. Never the key, never the HMAC.

### 2.4 Client guidance

- When `requests_per_minute` or `max_concurrent_requests` is set, the `instructions` text and the focused-review prompt add one sentence after "in parallel if you can": "The server queues model calls to stay within its configured rate limit, so parallel focused reviews wait for each other instead of failing." Without either setting the text does not change.

### 2.5 Tests and canaries

- Window: N+1 requests within 60 s on a fake clock → the last waits until the first leaves the window; concurrency cap; FIFO order with three waiters; ctx cancel while waiting frees the place.
- 429: `Retry-After` seconds and date; `x-ratelimit-reset-requests` forms; doubling without headers and reset after a success; a second caller waits for the cool-down without sending a request; `max_rate_retries` exhausted; wait longer than `max_rate_wait_seconds` fails at once without sleeping.
- Registry: two runs with the same base URL and key share a limiter; a different key gets another; the key never appears in the registry's printed form or logs (scan the log output).
- Integration: four concurrent focused `pr_review` runs against a fake endpoint that answers 429 above 3 requests per fake minute, `requests_per_minute` = 3: all four succeed, no request is answered 429, metadata counts the waits.
- **[canary]** let each caller retry on its own (no shared cool-down): the second-caller case fails.
- **[canary]** count only first attempts in the window (not retries): the window case with a retry fails.
- **[canary]** sleep for a wait longer than `max_rate_wait_seconds`: the fail-at-once case fails (the fake sleeper records a sleep).
- **[canary]** key the registry by base URL only: the different-key case fails.

1. `feat(llm): limit requests per minute and in flight per endpoint`
2. `feat(llm): cool an endpoint down on HTTP 429 for every caller`
3. `feat(review): report rate-limit waits` (metadata, note, client guidance; all tools that call the model)

## 3. WP-8c — Fallback model chain (Opus)

### 3.1 Configuration

Up to three fallbacks, in order. TOML:

```toml
[[llm.fallback]]
model = "second-model"
# base_url = "https://fallback.example/v1"   # default: llm.base_url
# context_window = 128000                    # default: resolved like llm.context_window (X-15)
# max_output_tokens = 4096                   # default: llm.max_output_tokens
# reasoning_effort = "low"                   # default: unset
# timeout_seconds = 120                      # default: llm.timeout_seconds
```

Env (index 1–3): `REVIEW_MCP_LLM_FALLBACK_<N>_MODEL`, `_BASE_URL`, `_CONTEXT_WINDOW`, `_MAX_OUTPUT_TOKENS`, `_REASONING_EFFORT`, `_TIMEOUT_SECONDS`; secret `REVIEW_MCP_LLM_FALLBACK_<N>_API_KEY`. Env entry N exists when its `_MODEL` is set; env replaces the file's entry N field by field. Gaps (2 without 1) are a validation error.

**API key rule (leak guard):** a fallback uses its own `_API_KEY` when set. Without one it uses the primary key **only when its base URL equals the primary's** (after normalisation); a fallback on another host without its own key sends no key. The primary key is never sent to another host. `server_info` shows for each fallback: model, redacted base URL, whether a key is set ("own", "primary", "none"), resolved context window. Temperature and seed are shared with the primary.

### 3.2 When the chain moves on

A model call moves to the next model in the chain when, for the current model:

1. its own retries are used up for `upstream` (5xx), `timeout` or `transport`; or
2. it is rate limited and either `max_rate_retries` is used up or the needed wait exceeds `max_rate_wait_seconds` (owner default 2); or
3. (pr_review, pr_improve, pr_describe, pr_ask: wherever a same-model re-ask exists) the answer is still unusable after that re-ask (`ErrFallbackEligible` from the parse path): the next model gets the original prompt once.

It does **not** move on for: `auth` (401/403), `bad_request`, a canceled or expired context, `config_invalid`. Those end the call as today.

Before sending to a fallback, the prompt's estimated tokens (the run's estimate and the fallback's `token_estimate_factor` = the primary's) plus its max output must fit the fallback's context window; otherwise the fallback is skipped for that call (counted, §3.4).

### 3.3 Run behaviour

- **Sticky:** once a call of a run was served by fallback K, later calls of that run start at K (default 6). A new run starts at the primary again.
- Each fallback has its own limiter by §2.2 (same base URL and key → shared limiter, which is correct: the gateway limits the key).
- The chain is built per run in `wiring.NewLLM` from the configuration; it implements the existing `Completer` interface, plus whatever narrow method the parse path needs to ask for the next model. Prefer one method; any wider change is a DESIGN-QUESTION.

### 3.4 Result and messages

1. `metadata.model` is the model that served the last call. New `metadata.models_used`: the distinct models that served calls, in order of first use. New `metadata.fallback_calls`: calls served by a fallback.
2. Note when `fallback_calls` > 0: "N model calls were served by a fallback model (`second-model`) because the primary model was unavailable (rate limited)." The reason is the class of the first move: `rate limited`, `server error`, `timed out`, `unreachable`, `unusable answer`. Model names are configuration, not secrets.
3. Note when a fallback was skipped for size: "The fallback model `x` was skipped for N calls because the prompt does not fit its context window."
4. When every model failed: the error of the **primary** is reported (its class and sentence), with the note "All N fallback models failed as well." The run fails as today.

### 3.5 Tests and canaries

- Each trigger moves on; each non-trigger does not (auth, bad request, cancel).
- Sticky within a run; a new run starts at the primary.
- Key rule: same host without own key → primary key sent; other host without own key → no `Authorization` header; own key wins. Verified on the fake server's received headers.
- Size skip; all-fail reporting; unusable answer after re-ask → next model once.
- Integration: a primary that answers 503 → pr_review served by fallback 1, `models_used` both models in order, note text.
- **[canary]** send the primary key to every fallback: the other-host case fails.
- **[canary]** move on after `auth`: the 401 case fails.
- **[canary]** not sticky (every call starts at the primary): the sticky case fails (the fake primary sees a second request).
- **[canary]** skip the size check: the size-skip case fails.

1. `feat(config): configure fallback models`
2. `feat(llm): fall back to the next model when a call cannot be served`
3. `feat(review): report fallback use` (all tools)

## 6. WP-8e — Queue jobs instead of refusing them (Sonnet; rc.4)

Found by the rc.3 acceptance (#32, Q2): the job store runs at most `jobs.MaxRunning` = 4 jobs and refuses a fifth with "too many background jobs are running; wait for one to finish". However, the multi-perspective instructions tell the client to run five focus areas in parallel, so the fifth focused review fails. Serve mode has the same shape: `serve.max_concurrent_calls` (default 4) answers `server_busy` at once. Now that model calls are rate-limited (X-37), the jobs should wait their turn too. Owner approved 2026-10-16.

### 6.1 Job store (stdio)

1. `Store.Start` no longer refuses when `MaxRunning` jobs run. The new job is **queued** (new state `queued`) and starts, in arrival order (FIFO), when a running job finishes. `Start` still returns its id at once.
2. A new limit `MaxQueued` = 32 caps the queue. Only when `MaxQueued` jobs already wait does `Start` fail with `ErrTooMany`, which gets the new sentence "too many background jobs are running or waiting; wait for one to finish".
3. Snapshots of a queued job:
   - state `queued`;
   - the new field `Position`, its 1-based place in the queue;
   - `Elapsed` counted from the moment it was queued. Once the job starts, `Elapsed` is the run time only.
4. A queued job is never evicted and never expires. `Close` fails every queued job with `ClosedSentence` without running it.
5. A queued job holds nothing but its run closure. That closure carries the request-scoped config and credentials exactly as a running job's does, and it is released when the job ends (X-10 unchanged).

### 6.2 Tool layer (stdio)

1. The call's `wait_seconds` counts from the call, queue time included. A job still `queued` or `running` when it ends answers with the job id. The status gets the new value `queued` next to `running`, and the schema is updated.
2. Sentence for a queued job: "The {noun} is waiting for a free slot (position N in the queue). Call `job_result` with job_id `…` to get the result."
3. `job_result` on a queued job waits as on a running one and reports the same status.

### 6.3 Serve mode

1. The concurrency gate waits for a free slot instead of answering `server_busy` at once, in arrival order, for as long as the call's context lives.
2. The new key `serve.max_queued_calls` (env `REVIEW_MCP_SERVE_MAX_QUEUED_CALLS`, default 32, range 0–1024) caps the waiting calls. 0 means today's behaviour: refuse at once. Above the cap the call gets `server_busy` as today.
3. `server_info` shows the new key.

### 6.4 Tests and canaries

- Store:
  - five jobs with `MaxRunning` 4: the fifth is `queued` at position 1 and starts when one finishes;
  - FIFO order with three queued jobs;
  - `MaxQueued` + 1 is refused with the new sentence;
  - `Close` fails the queued jobs, and they never run;
  - a queued job is never evicted.
- Tool layer: five concurrent focused `pr_review` calls on the stdio harness all succeed; a call whose `wait_seconds` ends while its job is queued answers with the queued sentence and the job id.
- Serve: with `max_concurrent_calls` 1 and `max_queued_calls` 1, the second call waits and succeeds and the third gets `server_busy`; with `max_queued_calls` 0 the second gets `server_busy`.
- **[canary]** refuse at `MaxRunning` again: the five-jobs case fails.
- **[canary]** start queued jobs in LIFO order: the FIFO case fails.
- **[canary]** the serve gate ignores `max_queued_calls`: the third-call case fails.

## 5. Backlog created by this spec

- Machine-wide limiter shared by several processes (lock file in the cache directory), for users who run several client sessions against one gateway.
- Run-level fallback for `DoesNotFit`: prepare the run again with the first fallback whose context window fits.
- Token-per-minute limits (`x-ratelimit-*-tokens`).
- Per-tool model selection (for example a cheaper model for `pr_describe`).
