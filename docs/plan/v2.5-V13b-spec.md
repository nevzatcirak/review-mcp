## 0. Decisions

- **X-41, part b — Consumer impact.** A `related` item may also be a **repository** (optionally a branch of it). review-mcp fetches it read-only at one commit, pinned when the run starts, through the repository-context machinery (X-22). From the primary diff it derives the changed contract surface: changed contract files, the identifiers that disappear or change in them, and the changed exported symbols. It searches each related repository for those identifiers. The hits are fenced, budgeted context. With repository tools on (X-43), the model may also read and search inside those repositories. A finding located in a related repository is listed in the overview with a link to the file and line at the pinned commit, and is never anchored inline. A search with no hits is reported as "no use found at <commit>", never as "no impact". Nothing in a related repository is built or run (R-1).

**Owner defaults (approved 2026-10-19):**
1. **Argument.** `related` on `pr_review` and `pr_ask` takes pull request URLs (as in V-13a) **and repository URLs**, together at most 4 items. A repository URL names the repository or a branch of it in the provider's own browse form (§1.1); without a branch, the repository's default branch is used. `pr_describe` and `pr_improve`: backlog, as in V-13a.
2. **Needs repository context.** Repository items are read only with `context.repo.enabled` (stdio only, X-22). Otherwise each repository item is `failed` with the reason `repo_context_off`, and the run goes on. Pull request items are unchanged.
3. **Pinned commit.** The commit is whatever `git fetch` brings for the branch (or the remote's `HEAD` for the default branch) at the start of the run. It is reported in the result as `commit`, used for every read, search and link, and never changes during the run. No provider REST call is added.
4. **What is searched.** Up to `related.max_identifiers` identifiers (operator key, default **20**, range 1–50), derived deterministically from the primary diff (§2.1). Search caps per repository: 5 hits per identifier, 30 hits in total, 2 lines of context, the RC-7 timeouts.
5. **Budget.** Repository items share `related.max_tokens` with pull request items, equally among the readable items, exactly as in V-13a. The related block stays after the issue block and before repository context, only in the room the primary diff leaves.
6. **Relations in the repository config.** The reviewed repository's `.review-mcp.toml` (base revision) may declare related repositories (`[[related.repos]]`, §3.2). They are used only when the call passes no `related`, only with the operator key `related.from_repo_config` = true (default **false**), and only when they resolve to a configured provider. The result names every item read this way (`source: "repo_config"`). A call's own `related` always wins and is always allowed.
7. **Repository tools in related repositories.** With `context.repo.max_tool_rounds` > 0, the three tools of X-43 take an optional `repo` argument naming a readable repository item (`R1` to `R4`). The same path rules and the same `max_tool_tokens` budget apply. Related **pull request** items are not readable by tools in V-13b (backlog).
8. **Incremental runs (X-36).** A repository item is recorded by URL and branch, not by commit, because a default branch moves for reasons unrelated to the pull request. An incremental run searches it again at its new pinned commit with the identifiers of the files it reviews, and the overview names that commit. A changed set of related items (added, removed, or a different branch) still means a full review, as in V-13a.
9. **Focused runs and merged publish:** unchanged from V-13a (`related` with `focus` or `findings` is refused). **A review in parts:** no related block, with the existing note.
10. **Version:** `2.5.0-rc.1`.

## 1. WP-13a — Repository items (Opus)

### 1.1 Repository URLs

1. Each provider factory gets `ParseRepoPath(remainder string, query url.Values) (namespace, repo, branch string, err error)` next to `ParsePRPath`, with the same escaping rules (split on `/` first, path-unescape each segment, reject `.` and `..`). Accepted forms (the branch part is optional):

   | Provider | Repository | With a branch |
   |---|---|---|
   | GitHub | `/{owner}/{repo}` | `/{owner}/{repo}/tree/{branch…}` |
   | Gitea | `/{owner}/{repo}` | `/{owner}/{repo}/src/branch/{branch…}` |
   | GitLab | `/{group…}/{repo}` | `/{group…}/{repo}/-/tree/{branch…}` |
   | Bitbucket Server | `/projects/{KEY}/repos/{slug}` or `…/browse` | `…/browse?at=refs/heads/{branch}` (only this query key, only `refs/heads/`) |

   - `{branch…}` is every remaining segment joined with `/`. Since a tree URL can also name a path inside the repository, a branch URL must point at the branch root; a longer URL is read as a longer branch name, which then fails with `branch_not_found` (§1.3). The docs say so plainly.
   - A trailing `.git` on the repository name is dropped.
   - A pull request URL keeps matching `ParsePRPath` first; only a URL that is not a pull request URL is tried as a repository URL.
2. **Branch names** are checked before any git call: 1 to 255 bytes; characters `A–Z a–z 0–9 / . _ -`; no `..`, no `//`, no leading or trailing `/` or `.`, no segment starting with `.` or `-`, not ending in `.lock`, not `HEAD`. A refused branch is `url_malformed`.
3. **Resolver.** `Resolver.ResolveItem(rawURL) (Item kind, PRRef or RepoRef, Provider, error)`. It matches the host and base path exactly as `Resolve` does (pinned hosts; no token to a host that is not configured), then tries `ParsePRPath`, then `ParseRepoPath`. `RepoRef` holds `Kind`, `Namespace`, `Repo`, `Branch` ("" = default) and `URL`. No network I/O.
4. **`related.Validate`** keeps its checks and messages, with one change: the per-item message becomes `related[i] must be an http or https pull request or repository URL without credentials`. Before `Normalize` drops the query, the Bitbucket Server `at` value is kept for `ParseRepoPath` (only that key).
5. **Ignored items:** a repository item naming the primary's own repository is `ignored` with the reason `primary_repository` (its contents are already repository context). Two items naming the same repository and branch are `ignored` / `duplicate`.

### 1.2 Fetching at a pinned commit

1. `gitctx.Runner.EnsureBranch(ctx, repo Repo, branch string) (Checkout, error)`. It is `Ensure` with a different ref, and every RC rule applies unchanged: the cache layout, the lock, the redirect guard (`checkURL`), credentials only through the child environment, no token on disk or in argv, the auth scheme order, the partial-clone filter, `--depth=1`, no tags, no submodules, `MaxRepoBytes`, the fetch timeout.
   - Remote ref: `refs/heads/{branch}`, or `HEAD` when the branch is "".
   - Local ref: `refs/review-mcp/branch/{hex(sha256(branch))[:16]}` (`refs/review-mcp/branch/default` for ""), so that a branch name never forms a path or a ref expression.
   - The commit is the local ref's commit after the fetch (`resolve`). There is no SHA to compare with, so no `sha_mismatch` check; the commit is the pin.
   - The cache entry is the same as the repository's pull request checkouts (same host/namespace/name directory), so one bare repository serves both.
2. New fixed reason in `gitctx` (with a note): `branch_not_found` (the remote has no such ref: git's "couldn't find remote ref"). The other failed reasons of a repository item are `gitctx`'s existing ones, passed on as they are: `not_found`, `timeout`, `too_large`, `redirect`, `git_unavailable`, `git_failed`, `busy`, `cache_unusable`, `unsupported`; and `auth`, reported as `unauthorized` (git cannot tell 401 from 403 once both auth schemes are refused). *(Aligned with the code in the WP-13a review, DQ-7.)*
3. Reads are sequential, in argument order, after the pull request items, each under the run's context. A failure never fails the run.

### 1.3 Accounting

1. `coverage.related[]` entries of repository items carry, in addition to `url`, `status`, `reason`:
   - `kind`: `"repository"` (absent on pull request items, so a 2.4 result is byte-identical);
   - `branch`: the branch, or `""` for the default branch;
   - `commit`: the pinned commit (40 hex), when fetched;
   - `identifiers`: how many identifiers were searched;
   - `matches`: hits found, `matches_shown`: hits placed in the prompt;
   - `source`: `"repo_config"` only for items read from the repository config (§3.2).
   All new fields are omitted on pull request items; the schema declares them with `additionalProperties: false` kept.
2. Status values for repository items:
   - `full`: every hit was shown;
   - `partial`: some hits were cut by a cap or the budget (the note says which);
   - `no_use_found`: the search ran and found nothing (new status, §2.4 note);
   - `not_placed`: fetched but not in the prompt; reasons `did_not_fit`, `review_in_parts`, `off`, `nothing_to_review`, and the new `no_contract_change` (the primary diff gave no identifier, so nothing was searched);
   - `failed`: reasons as in V-13a plus `repo_context_off`, `branch_not_found` and the `gitctx` reasons;
   - `ignored`: `primary_repository` or `duplicate`.
3. **Logs:** the item's index, kind, provider kind, status, reason and counts. Never the URL path, the branch, the commit, an identifier, a path or a hit.
4. **`server_info`** reports `related.max_identifiers` and `related.from_repo_config`.

### 1.4 Tests and canaries

- the URL table per provider, including nested GitLab groups, branches with `/`, Bitbucket `at`, `.git` suffix, and each refusal (no I/O);
- the branch-name table;
- `EnsureBranch` on the fixture git server used by the `Ensure` tests: default branch, named branch, missing branch (`branch_not_found`), the redirect guard, no token in argv or on disk (asserted as for `Ensure`);
- a repository item in serve mode or with `context.repo.enabled` false → `failed` / `repo_context_off`, no git call;
- a 2.4 result with only pull request items renders and serialises byte-identically (existing goldens unchanged);
- every new coverage case validated against the declared schema.

**Canaries:**
1. Let a branch name with `..` through → the branch-name test fails.
2. Build the local ref from the raw branch name → the ref-name test fails.
3. Emit `kind` on a pull request item → the byte-identical golden fails.

Commits:
1. `feat(provider): parse repository URLs`
2. `feat(gitctx): fetch a branch at a pinned commit`
3. `feat(related): accept repository items`

## 2. WP-13b — Contract surface, consumer search, prompt and findings (Opus)

### 2.1 The changed contract surface

A new pure function `related.Surface(files []provider.FilePatch, flt *filter.Filter, max int) []Identifier`. Input: the primary diff after filtering, the full change (an incremental run passes the files it reviews).

1. **Contract files** are tier 1 and tier 2 of `filter.ContractTier` (V-13a §1.3), plus `related.contract_globs`.
2. **Identifiers from contract files.** For each contract file's patch, tokens are taken from removed lines and added lines with the pattern `[A-Za-z_][A-Za-z0-9_]{2,99}`:
   - **gone**: on a removed line and on no added line of the same file (a renamed or removed field, operation or message);
   - **changed**: on a removed line and on an added line of the same hunk (a field whose type, requiredness or format changed).

   Only removed-line names matter: a consumer can only use a name that existed before.
3. **Routes from API descriptions** (tier 1, YAML or JSON): a removed line whose key is a path (`^\s*["']?(/[^"'\s:]*)["']?\s*:`) gives the route's **static prefix**: the segments before the first `{…}` segment, kept only when it has at least one static segment of 3 or more characters. It is searched as a fixed string without word boundaries.
4. **Changed exported symbols:** `gitctx.ExtractSymbols` on all files of the diff, the symbols whose definition line was removed or changed (rank as today).
5. **Stop list.** Tokens in the stop list are dropped. The list is data in `internal/related/data/stopwords.go` and documented in `docs/review.md` (§4 item 4): schema keywords (OpenAPI/JSON Schema, protobuf, GraphQL, Avro, Thrift, WSDL), type names (`string`, `integer`, `int32`, `boolean`, `object`, `array`, …), and common words (`the`, `and`, `description`, `example`, `summary`, `true`, `false`, `null`, …).
6. **Order and cap:** gone (in diff order), then routes, then changed, then exported symbols; duplicates dropped (first kind wins); at most `max`. What the cap drops is counted in the note.

### 2.1a Surface first, then fetch *(added in the WP-13a review, DQ-5)*

The surface (§2.1) is derived before any repository item is fetched. When it is empty, no repository item is fetched: each readable one is `not_placed` with the reason `no_contract_change`, without `commit`, and the note of §2.4 item 3 is given once. A fetch is only made when there is something to search for. In WP-13a a fetched item without a run reason was `not_placed` without a reason; that state disappears here.

### 2.2 Searching a consumer

1. For each readable repository item: `Runner.Grep`-style fixed-string search on the pinned commit (`git grep -n -F -I`, word-bounded for identifiers, not for routes), offline (`protocol.allow=never`), the RC-7 limits, the operator's `ignore.*` filter, test files included (consumers' tests are consumers).
2. A repository item from the repository config with `paths` searches only below those prefixes (path rules as X-43).
3. Caps: 5 hits per identifier (the first by path order), 30 per repository, 2 lines of context.
4. The hits go through the `repoctx` rendering (sanitised, fenced, whole entries), within the item's share.

### 2.3 Prompt

1. A repository item's section in the related block:
   - its line: `R{n} — repository {namespace}/{name}, branch {branch or "default"}, commit {first 12 hex}`;
   - the identifiers searched, by kind: `Removed or renamed: …`, `Routes: …`, `Changed: …`, `Changed exported symbols: …` (sanitised; at most the cap);
   - the hits as `path:line` entries with context, fenced;
   - or the sentence `No use of these identifiers was found at this commit. Text search does not see dynamic or generated uses.`
2. The fixed instruction for related items gets one more paragraph when a repository item is placed: report a consumer that uses a removed or renamed identifier or route, or uses a changed one in a way the new contract breaks; tag the finding with the item label and the consumer's file and line; say "needs verification" when only the name matches.
3. The block is fenced as untrusted data, as in V-13a. The primary diff always wins.

### 2.4 Findings and notes

1. A finding tagged with a repository item's label and located in a file of that repository (a hit file, or a file a tool read) is listed in the overview's cross-repository section with a link built by that item's provider: `FileLineURL(ref, &PullRequest{HeadSHA: commit}, path, line)`. Each provider's result must be a link to the file **at that commit**; this is tested per provider. A finding on the primary's own files is placed inline as today (WP-11d rule: by file).
2. A finding tagged with a repository item but naming a file the run never saw is listed without a link, with "(location not verified)".
3. Notes (fixed sentences):
   - `No use of the changed identifiers was found in {namespace}/{name} at {commit 12}. Text search does not see dynamic or generated uses, so this is not a statement that nothing is affected.`
   - `The pull request changes no contract file or exported symbol, so the related repositories were not searched.`
   - `{n} of the changed identifiers were not searched (limit {max}).`
   - `Hits in {namespace}/{name} were cut at {k} (limit).`
4. The overview's coverage section: the existing related line counts repository items too; a repository item shows `searched {i} identifiers at {commit 12}: {m} matches` or `no use found at {commit 12}`.

### 2.5 Incremental record

The `review-mcp:related:` hidden record gets repository entries, encoded like the pull request entries (base64 JSON: `{"k":"repo","u":url,"b":branch or "-"}`), with no commit *(wording aligned with the code in the WP-13b review, DQ-7)*. A repository item that failed stays in the recorded set (its URL and branch are known); an item whose URL could not be resolved is a change, as in V-13a (WP-13b DQ-1). Old records (pull request entries only) parse as before. The comparison rule is owner default 8: a different set (including a different branch) → full review with the existing note; a moved commit → no change.

### 2.6 Tests and canaries

- `Surface` on fixture patches: OpenAPI rename, protobuf field removal, GraphQL type change, a route rename, a type-only change (`changed`), stop-word filtering, the cap and its count;
- consumer search on a fixture repository: hits, no hits (note and `no_use_found`), the caps, `paths` confinement, offline asserted;
- the related block with a mix of a pull request item and a repository item, under a sweep of context windows (the primary diff never trimmed);
- the fence holds hit text containing the fence string and "ignore previous instructions";
- link per provider at the commit; a finding in a file never seen gets no link;
- incremental: moved commit → incremental run; branch changed → full review.

**Canaries:**
1. Count a token that appears only on added lines as gone → the surface test fails.
2. Report `full` when no hit was found → the `no_use_found` test fails.
3. Link a consumer finding at the branch instead of the commit → the per-provider link test fails.

Commits:
1. `feat(related): derive the changed contract surface`
2. `feat(related): search related repositories for the changed identifiers`
3. `feat(review): report consumer impact`

## 3. WP-13c — Repository tools in related repositories; relations from the repository config (Opus)

### 3.1 Tools

1. With `max_tool_rounds` > 0 and at least one readable repository item, the tool schemas of `read_file`, `list_dir` and `search` get an optional `repo` parameter: an enum of the readable repository items' labels (`R1`…`R4`). Absent means the primary's head commit, as in 2.4. Without readable repository items the schemas are byte-identical to 2.4 (golden request).
2. A call with `repo` reads that item's checkout at its pinned commit, with the same path rules, caps and fence; the fixed result header names the label.
3. `coverage.repo_context.tools.calls[]` gets `repo` (the label, omitted for the primary). The budget `max_tool_tokens` is shared by all repositories.
4. The tool instruction block gets one sentence naming the labels and their repositories.

### 3.2 Relations from the repository config

1. New repository-config keys (X-40 allow-list):

   ```toml
   [[related.repos]]
   url = "https://git.example/team/web-ui"   # a repository URL, §1.1 forms
   branch = "main"                           # optional
   paths = ["src/api/"]                      # optional, at most 10 prefixes
   ```

   At most 4 entries. Invalid entries are reported like other invalid keys (`repo_config.status` and notes); valid ones are kept.
2. Used only when the call passes no `related`, and only with the operator key `related.from_repo_config` = true. Otherwise the key `related.repos` is listed in `repo_config.ignored` (a list of key names, as today) with one note: `The repository config names related repositories, but reading them is turned off by the operator (related.from_repo_config).`
3. Each declared URL goes through `ResolveItem`: a URL that matches no configured provider is `failed` / `url_not_configured` (it can never add a host). Each read item has `source: "repo_config"`, and the overview names it.
4. `pr_info` reports declared relations without reading them.

### 3.3 Tests and canaries

- a tool call with `repo: "R1"` reads the consumer at its commit; an unknown label is `invalid_arguments`; a path outside is `not_allowed`;
- schemas byte-identical without repository items;
- repository config: off → ignored with the reason and the note; on → read with `source`; a call's `related` wins; an unconfigured host fails without a request.

**Canaries:**
1. Let `repo` name a pull request item → the label test fails.
2. Read the repository config's relations with `from_repo_config` false → the off test fails.

Commits:
1. `feat(repotools): read related repositories`
2. `feat(repocfg): declare related repositories`

## 4. WP-13d — `pr_ask`, `pr_info`, `server_info`, docs, acceptance (Sonnet)

1. **`pr_ask`:** repository items with the same surface, search, block and tools; the answer may cite consumer locations with links.
1a. **Stop-listed removals are named** *(added in the WP-13b review, DQ-10)*: a **gone** identifier dropped only by the stop list (for example `name`, `type`) is not searched, but the repository section names it on one line, `Removed but not searched (too common): …`, so the model is not left to read the absence as "no use". The coverage counts do not change. Same in `pr_review`.
2. **`pr_info`:** repository items are resolved (no read, no fetch) and listed with `kind`, `branch` and status `not_read`.
3. **MCP prompt `review_linked_prs`:** accepts repository URLs among the set; repository items are passed as `related` to every pull request's call and never reviewed themselves.
4. **Docs:**
   - `docs/review.md`, in the "Related pull requests" section (renamed "Related pull requests and repositories"), a subsection "Repository items and consumer impact": the URL forms and the branch caveat, the pinned commit, what is searched (the surface rules and the stop list), the honesty sentence, the caps, the cost, repository tools in related repositories, the repository-config relations and the operator switch;
   - `docs/repo-config.md` `[[related.repos]]`; `docs/ask.md` and `docs/pr-info.md` repository items; `docs/setup.md` keys; `docs/troubleshooting.md` every new reason and note;
   - decisions doc: X-41 part b with every settled DQ;
   - CHANGELOG `## [Unreleased]` planned as `2.5.0-rc.1`.
5. **Acceptance (owner, after the release; stdio, repository context on; cross-provider):**
   - **Fixture:** a throwaway pull request in this repository that renames `userName` to `displayName` in an OpenAPI file under `examples/acceptv25/`; a consumer branch on the GitLab throwaway project whose client code reads `userName`; the same project's default branch without such code.
   - **Q1:** `related` = the consumer branch URL → item `full`, `commit` reported, a cross-repository finding with a link to the consumer's line at that commit, nothing inline for it.
   - **Q2:** `related` = the repository URL (default branch) → `no_use_found` and the honesty note, word for word.
   - **Q3:** Q1 with `max_tool_rounds` 3 → if the model reads the consumer, calls carry `repo: "R1"` (not exercised if the model does not ask; recorded as such).
   - **Q4:** a base branch carrying `[[related.repos]]`: `from_repo_config` false → ignored with the note; true → read with `source: "repo_config"`.
   - **Q5:** `context.repo.enabled` false → `failed` / `repo_context_off`; the pull request review goes on.
   - **Q6:** a branch that does not exist → `failed` / `branch_not_found`.
   - **Q7:** an incremental run after a new commit to the primary → incremental, the consumer searched again, its commit named.
   - **Q8:** `pr_ask` "Which code in the related repository uses the renamed field?" with the consumer branch.

Commits:
1. `feat(ask): search related repositories`
2. `feat(tools): list repository items in pr_info and server_info`
3. `docs: document consumer impact`

## 5. Backlog created by this spec

- Repository tools inside related pull requests (their head commits).
- `pr_describe` and `pr_improve` with `related`.
- Structured parsing of API descriptions (OpenAPI, protobuf, GraphQL) instead of token rules.
- Discovery of related repositories as a suggestion list (never automatic reads).
- Related items in focused runs.
