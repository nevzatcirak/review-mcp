# 2.5.x — WP-15: behaviour on older git (2.31 to 2.43)

| | |
|---|---|
| Status | Approved by the owner 2026-10-20 (run in parallel with WP-14a). |
| Origin | The local session reported that two tests fail with the host's git 2.43 on an untouched `main`: `gitctx/TestFileAtBlobMissing` and `repotools/TestToolsOnRealRepository`. Both pass in the gate container, whose git is newer. The documented minimum is git 2.31 (`gitctx.MinGitVersion`, RC-2). |
| Hypothesis (to prove or refute, not to assume) | `GIT_NO_LAZY_FETCH` exists only from git 2.44. On 2.31–2.43 git ignores it, so reading a blob the partial clone lacks starts a lazy fetch from the promisor remote. `protocol.allow=never` should then stop that fetch, but the error git prints differs. As a result the read is not classified as `blob_missing`. A worse outcome would be a lazy fetch that succeeds, for example over the `file` protocol of the test fixture. |
| Why it matters | Repository context, repository tools and the V-13b consumer search all read offline on the promise "a read never fetches". On a git without `GIT_NO_LAZY_FETCH`, that promise rests on `protocol.allow=never` alone. If any path lets a fetch through, the rule "no network during reads" is broken for users on git 2.31–2.43. If none does, only the classification is wrong. |
| Packages | WP-15a (Opus): investigation and fix. One draft PR "v2.5.x: older git (WP-15)". |
| Release | The next 2.5.x release, together with or separate from WP-14a; the owner picks. |

## 1. Investigation (first commit and report; no production change before it)

1. **Matrix.** Run the `gitctx`, `repotools`, `repoctx` and `related` tests in containers with git **2.31**, **2.39**, **2.43**, **2.44** and the gate container's git. Use distribution packages or a source build pinned by version; record how each git was obtained. Report per version: pass or fail, and for each failure the test, the error class and git's stderr. Never print a token; the tests use no credentials.
2. **The fetch question.** Write one diagnostic test (kept as a regression test) that must hold on every version of the matrix:
   - the checkout's promisor remote is a local fixture that records every connection (a `file://` remote whose directory is watched, plus an `http://127.0.0.1` remote served by a counter in the test);
   - read a missing blob through `FileAt`, `SearchText`, the consumer search (`SearchTerms`) and `Grep`;
   - assert **zero** connections and zero new objects in the checkout, on every git version.
3. **Report before any fix:**
   - which hypothesis holds: a misclassification only, or a real fetch;
   - which call sites set `GIT_NO_LAZY_FETCH` and `protocol.allow=never`, and how (`-c` or environment; does the lazy-fetch child inherit them on 2.31–2.43?);
   - DESIGN-QUESTIONs with recommendations.

   Stop after the report, then wait for the architect.

## 2. Fix (settled in the review of the §1 report, PR #57, 2026-10-21)

**Findings of §1, in short.** No read fetched anything on any of 13 gits. However, on every git without `GIT_NO_LAZY_FETCH`, a guarded read **starts** a lazy-fetch child that only `-c protocol.allow=never` stops; canary C1 shows a real fetch without it. The misclassification is a different effect: on git 2.39 to 2.44.x, backports included, git dies after a failed or disabled lazy fetch. 2.45.0 is the first release that reports the object as missing. An exit 141 (SIGPIPE) race can make this worse. On those versions a search that meets a missing blob fails as a whole.

**Decision X-45: offline reads go through a read view.** (§1 DQ-1 option A; DQ-2 "a fetch can happen" branch.)

1. **The read view.** A bare repository that review-mcp creates once per cache root, next to the hosts, under the cache's own validation (a real directory, never a link, inside the root).
   - It has no `extensions.partialClone`, no remote, no hooks and no refs.
   - Its `extensions.objectFormat` is created per object format (`sha1`, `sha256`).
2. **Every offline read** uses `--git-dir=<view>`, with `GIT_OBJECT_DIRECTORY=<checkout>/objects`. The two existing guards stay as further layers (`-c protocol.allow=never`, `GIT_NO_LAZY_FETCH=1`).
   - **Offline reads:** every call site listed in the §1 report §3: `rev-list --missing=print`, `ls-tree`, `grep`, `cat-file --batch` / `--batch-check`, `diff --name-only`.
   - **Fetches** (`Ensure`, `EnsureBranch`) are unchanged.
3. **Shallow history (must be proven first).** The checkouts are `--depth=1`. A read that walks from a commit (`rev-list`, `diff` between two commits) must behave in the view exactly as in the checkout. In particular, a parent missing because of the shallow boundary must not become an error.
   - If the view needs the checkout's `shallow` file, the fix says how it gets it, without writing into the checkout. A view per checkout is acceptable if one shared view cannot work.
   - This is the first test of the first fix commit, on every version of the matrix.
4. **Classification.** No stderr patterns are added. Through the view, every version reports a missing object as git 2.45+ does, and the existing `blob_missing` handling applies.
5. **What the tests assert (§1 DQ-3).**
   - `TestReadsNeverFetch` gets outcome assertions:
     - FileAt → `blob_missing`;
     - SearchText, SearchTerms and Grep → no error, the hit in the present file, and `SkippedBlobs > 0`.
   - `TestFileAtBlobMissing` and `TestToolsOnRealRepository` pass unchanged on every version of the matrix.
   - **Canary:** remove the view, and `TestReadsNeverFetch` fails on 2.43.0 and 2.44.1. C1 (protocol layer) stays as it is.
6. **Test fixes:**
   - `TestNoLazyFetchEnvironmentAlone` is gated at git ≥ 2.45.0 (§1 DQ-5).
   - `TestOfflineBlocksLazyFetch` sets `uploadpack.allowAnySHA1InWant=true` in its fixture (§1 DQ-6).
7. **CI (§1 DQ-4).** A Linux job builds git **2.31.0**, **2.43.0** and **2.44.1** from the kernel.org tarballs, pinned by SHA-256, on `ubuntu:22.04`, cached by tarball hash. It runs the whole `gitctx`, `repotools`, `repoctx` and `related` packages with each git.
8. **Windows (§1 DQ-8).** Add one real-git Windows test of a read through the view: FileAt of a present blob and of a missing blob, with the local `git` and no http-backend. It runs in the existing `gitctx-windows` job. If Windows git cannot run it, the report says so, and the docs mark the view as not verified on Windows.
9. **Docs (§1 DQ-7):**
   - `docs/repo-context.md`: reads use a view with no promisor, so no supported git can start a lazy fetch; git 2.31 stays the minimum, with no behaviour difference across versions. Replace the sentence that `protocol.allow=never` "alone blocks lazy fetches".
   - `docs/setup.md`: the same in one line.
   - Decisions doc: **X-45**.
   - CHANGELOG `[Unreleased]` (planned 2.5.1), Fixed: on git 2.39 to 2.44, a read of a file over 1 MiB failed instead of being reported as not fetched, and a search that met one failed as a whole; and on git without `GIT_NO_LAZY_FETCH`, only one setting stopped a lazy fetch.
