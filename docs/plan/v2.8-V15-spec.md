## 0. Decisions

1. **Two tools** (owner): `pr_list_review_requests` (pull requests that ask the token's user for a review) and `pr_list_authored` (pull requests the token's user opened). One shared engine and one result shape.
2. **Reviewer by default, assignees on request** (owner): `pr_list_review_requests` lists pull requests where the user is a requested reviewer. `include_assigned: true` adds those where the user is an assignee. Bitbucket Server has no assignees: there the argument adds nothing and the provider entry carries a note.
3. **Open pull requests only** (architect). Merged or closed lists are not in V-15. Draft pull requests are listed and flagged.
4. **Every enabled provider by default** (architect). The optional `provider` argument (`gitea`, `bitbucket_server`, `github`, `gitlab`) restricts the call to one. Providers are queried in parallel. Each one reports its own status; a failed provider never empties or silently shortens the list.
5. **One request per query, no per-item reads** (architect). A field the list endpoint does not carry is `null`, never fetched item by item. In particular `target_branch` is `null` on GitHub and Gitea.
6. **Limit** (architect): `limit` 1–100, default 30, applied to the merged list after sorting by `updated_at`, newest first. Each provider is asked for at most `limit` items. A provider that has more says so (`has_more`), and the result carries a note.
7. **URLs are built, not copied** (architect). An item's `url` is built by the provider from its configured web base, namespace, repository and number, exactly as the pull request URLs the resolver accepts. A URL in the response is never passed on. The built URL must resolve with `Resolver.Resolve` (contract case).
8. **Untrusted text** (architect). Titles and author names are third-party text: control characters and newlines removed, cut at 200 characters (titles) and 100 (names) at a character boundary, rendered only inside code spans (X-30), never logged.
9. **Serve mode** (architect): both tools are registered in serve. A provider whose token header is missing is skipped before any request, with status `no_token`. Read-only annotations.
10. **No new configuration keys** (architect).

### 1.0 Entry criteria (closed in the WP-19a report before production code)

For each item: the documentation link (or the source file and tag for Gitea), the minimum version that has it, and what the response carries. Anything that cannot be confirmed is a DESIGN-QUESTION, and the fixture records the assumption.

- **E1 Bitbucket Server / Data Center (7.0 and the current major):** `GET /rest/api/1.0/dashboard/pull-requests` with `state=OPEN`, `role=REVIEWER|AUTHOR`, `start`, `limit`, `order`. Which `order` value sorts by last update. That the request uses the token's own user (no `user` parameter is sent). The fields used: `id`, `title`, `draft` (and the version that adds it), `updatedDate`, `toRef.displayId`, `toRef.repository.slug`, `toRef.repository.project.key` (and the `~user` form of a personal project), `author.user.name`, the token user's entry in `reviewers[]` (`status`), `isLastPage`.
- **E2 GitLab (16.0 and the current version):** `GET /api/v4/merge_requests` with `state=opened`, `order_by=updated_at`, `sort=desc`, `per_page`, and per query: reviewer `scope=all&reviewer_id=<CurrentUser.ID>`; assignee `scope=assigned_to_me`; author `scope=created_by_me`. - **E3 GitHub (github.com and GHES 3.x as documented):** `GET /search/issues` with `q=is:pr is:open archived:false <qualifier>:<login>` and `sort=updated&order=desc&per_page=`. Qualifiers: reviewer `review-requested:`, assignee `assignee:`, author `author:`. Whether `review-requested:` includes team requests (expected: yes) and whether a request disappears once the user has reviewed (expected: yes). The search rate limit (expected: 30 requests per minute, separate from the core limit) and its error shape. The fields used: `number`, `title`, `draft`, `updated_at`, `user.login`, `repository_url` (parsed for owner and repository only, then checked against the configured API base), `total_count`, `incomplete_results`.
- **E4 Gitea:** `GET /api/v1/repos/issues/search` with `type=pulls`, `state=open`, `review_requested=true` / `assigned=true` / `created=true`, `page`, `limit`. The first Gitea release that has each of the three filters (source file and tag). Whether results are sorted by update, and whether a sort parameter exists. The fields used: `number`, `title`, `updated_at`, `user.login`, `repository.owner`, `repository.name`, `pull_request.draft` (and the release that adds it). How "more" is known (`X-Total-Count`).
- **E5 tokens without a person:** what each list returns for a Bitbucket project/repository HTTP access token, a GitLab project/group token, and a GitHub installation token (`ghs_`). Expected: an empty list or an error, never someone else's pull requests. Record it; the docs say so.

### 1.1 Types (`internal/provider`, new file `lists.go`)

```go
// ListRole selects which of the token user's pull requests a list holds.
type ListRole string

const (
	ListReviewer ListRole = "reviewer"
	ListAssignee ListRole = "assignee"
	ListAuthor   ListRole = "author"
)

// ListQuery is one list request: open pull requests only (X-48).
type ListQuery struct {
	Role  ListRole
	Limit int // 1..MaxListLimit, already validated by the caller
}

const MaxListLimit = 100

// ListedPR is one pull request of a list. Title and Author are untrusted
// third-party text, already cleaned with CleanListText.
type ListedPR struct {
	Ref          PRRef     // Kind, Namespace, Repo, Number; URL built by the provider (§0 item 7)
	Title        string
	Author       string
	TargetBranch *string   // nil when the list endpoint does not carry it
	Draft        *bool     // nil when the host does not report it
	UpdatedAt    time.Time
	// MyStatus is the token user's own reviewer status where the list
	// carries it (Bitbucket Server: "approved", "needs_work",
	// "unapproved"); "" otherwise. Never another user's status.
	MyStatus string
}

// PRList is one provider's answer to one ListQuery.
type PRList struct {
	Items   []ListedPR // newest update first, at most Limit
	HasMore bool
}

// PRLister is implemented by providers whose Capabilities().Lists allows
// at least one role. The contract suite checks both directions.
type PRLister interface {
	ListMyPullRequests(ctx context.Context, q ListQuery) (*PRList, error)
}

// ListCaps says which roles the host can list for the token's own user.
type ListCaps struct{ Reviewer, Assignee, Author bool }
```

- `Capabilities` gains `Lists ListCaps`. Bitbucket Server: reviewer and author. GitHub, Gitea, GitLab: all three.
- `CleanListText(s string, max int) string`: removes C0/C1 controls, U+2028/2029 and bidi controls, turns newlines and tabs into spaces, collapses runs of spaces, trims, cuts at `max` runes on a boundary. One implementation, used by all four providers.
- A query with a role the provider does not support is refused by `ListMyPullRequests` with an `unsupported` error before any request.
- `TargetBranch` passes `ValidBranchName`; a name that does not is `nil` (never shown raw).

### 1.2 Shared rules for every provider

- GET requests only, through the provider's existing client: auth, redirect guard, response size caps, fixed error reasons (X-6). No response body or provider error text is passed on.
- Identity: GitHub and GitLab call `CurrentUser` first (GitHub uses the login in the query; GitLab uses the ID). GitHub with `github.self_login` uses that login without `GET /user`. Bitbucket Server and Gitea filter on the authenticated user server-side and send no user name.
- `Ref` is built from parsed path parts only: namespace and repository go through the same validation as the resolver's `ParsePRPath`; an item whose parts do not validate is dropped and counted (`dropped` in the debug log, and a note in the tool result). `Ref.URL` is built by the same function that builds the PR URLs the provider's tests resolve.
- GitHub: `repository_url` must start with the configured API base followed by `/repos/`; otherwise the item is dropped and counted. A search answer with `incomplete_results: true` sets `HasMore`.
- GitHub search rate limit (403/429 from `/search`): a fixed `rate_limited` reason, no retry. The core limiter of X-37 is for the LLM and is not involved.
- Pagination: one page of `Limit` items. `HasMore` from the host's own signal (E1–E4). No second page in V-15.
- Logs (debug): provider kind, role, item count, dropped count, has_more. Never a title, name, namespace, URL or body.

### 1.3 Contract suite (`internal/provider/contract`)

New case `lists`, for every provider:
- `Capabilities().Lists` has a role ⇔ the provider implements `PRLister`.
- For each supported role: the fixture server answers one page with two items, one draft, one with a title carrying a newline, a control character and 300 characters. The result has both items, sorted, with cleaned and cut titles, `Draft` set where the host reports it, and URLs that `Resolver.Resolve` maps back to the same `PRRef`.
- An item whose repository path does not validate is dropped; an item whose response URL points to another host still gets the built URL.
- Every request the case sends is a GET (the harness records methods).
- An unsupported role (Bitbucket assignee) sends no request and returns `unsupported`.

### 1.4 Canaries (WP-19a)

Each proven on the reported commit's own tree: mutation, failing test name, failure line, tree hash before and after.
- (a) Bitbucket sends `role=REVIEWER` and `state=OPEN`. Mutation: omit `role`.
- (b) GitHub's reviewer query carries `is:pr`, `is:open` and `review-requested:<login>`. Mutation: drop `is:pr` (the fixture then returns an issue, which must not be listed).
- (c) Gitea sends `type=pulls` and `review_requested=true`. Mutation: send `created=true` instead.
- (d) GitLab's reviewer query sends `reviewer_id=<CurrentUser.ID>`. Mutation: send `scope=created_by_me`.
- (e) The item URL is built, not copied. Mutation: use the response's `html_url`/`web_url`/`links.self`.
- (f) `CleanListText` removes a newline and a bidi control and cuts at 200 runes. Mutation: skip the control removal.
- (g) Only GETs (contract). Mutation: send the GitLab query as POST.

## 2. WP-19b — the tools (Sonnet)

Commits:
1. `feat(provider): enabled providers without a pull request URL`
2. `feat(tools): pr_list_review_requests and pr_list_authored`
3. `feat(diag): list pull requests`

### 2.1 Resolver

`func (r *Resolver) Enabled() []Provider` builds (and remembers for `CloseIdleConnections`) one provider per enabled and registered kind, in a fixed kind order. No network I/O. In serve, the `tools.RequireCredentials` wrapper gets an equivalent that reports a kind without its token header as `no_token` and builds nothing for it.

### 2.2 Input

`pr_list_review_requests`:
- `provider` (optional): one of the four kinds; a kind that is not enabled is refused before any request with the configured kinds named.
- `limit` (optional): 1–100, default 30; out of range is refused, never clamped.
- `include_assigned` (optional, default false).

`pr_list_authored`: `provider`, `limit`.

### 2.3 Output (structured content with a declared output schema)

```
{
  role: "review_requests" | "authored",
  items: [{
    provider, url, namespace, repo, number, title, author,
    target_branch: string|null, draft: bool|null, updated_at,
    roles: ["reviewer"|"assignee"|"author"],
    my_status: string|null
  }],
  providers: [{ kind, status: "ok"|"failed"|"unsupported"|"no_token", reason: string|null, count, has_more }],
  notes: [string]
}
```

- `include_assigned`: the provider runs the reviewer and the assignee query; items are merged by `url`, and `roles` holds both where both apply. If one of the two queries fails, the provider's status is `failed` with the reason, and the items of the query that worked are kept, with a note naming the role that is missing.
- Sort: `updated_at` newest first, then provider kind, then URL. Cut at `limit`. When the cut drops items, or any provider has `has_more`, add `NoteListMore` ("More pull requests exist than this list shows; raise limit (at most 100) or name a provider.").
- `failed`: fixed reasons only (`auth`, `forbidden`, `rate_limited`, `timeout`, `unavailable`, `unsupported_version`, `bad_response`). Note `NoteListProviderFailedFormat` ("%s could not be listed (%s); the list does not include its pull requests.").
- Bitbucket with `include_assigned`: status stays `ok`; note `NoteListNoAssignees` ("Bitbucket Server has no assignees; only review requests are listed there.").
- GitHub reviewer list: one fixed note when GitHub is in the result: `NoteGitHubReviewRequests` ("On GitHub, a review request ends once you have submitted a review, and requests to your teams are included.").
- Empty result with every provider `ok`: the markdown says "No open pull requests ask for your review." / "You have no open pull requests." — scoped to the providers listed, never "nothing anywhere" when a provider failed.
- Markdown: a table or list with provider, `repo!number` as a link to the built URL, title in a code span, author in a code span, draft flag, target branch in a code span, updated date; then the per-provider line and the notes. No raw HTML (existing markdown tests apply).

### 2.4 Registration, description, annotations

- Both tools registered in stdio and serve. Annotations: read-only, idempotent, not destructive, open-world.
- `pr_list_review_requests` description: "Lists the open pull requests that ask you (the token's user) for a review on the configured providers, newest update first; with include_assigned also those assigned to you. Use an item's url with pr_review, pr_info or pr_ask. Read-only; no LLM call."
- `pr_list_authored` description: "Lists the open pull requests you (the token's user) opened on the configured providers, newest update first. Use an item's url with pr_info to see their reviewers and CI. Read-only; no LLM call."
- Instructions: one sentence after the first line: "To find pull requests to work on, call pr_list_review_requests or pr_list_authored."
- Tool-count assertions updated (stdio and serve).

### 2.5 diag

`review-mcp diag list review-requests|authored [--provider K] [--limit N] [--include-assigned] [--json]`: the same engine, the markdown or the structured result; exit 0 when every provider is `ok`, 1 when any is `failed`, 2 on usage. Existing diag subcommands unchanged.

### 2.6 Tests and canaries (WP-19b)

- Output schema validated against the declared schema for: normal, empty, one provider failed, `include_assigned` merged, Bitbucket note, every nullable field null.
- (h) Merge by URL with both roles. Mutation: append without merging (duplicate item).
- (i) A failed provider is reported, not dropped. Mutation: skip `failed` providers in `providers` and notes.
- (j) `has_more` gives `NoteListMore`. Mutation: ignore `has_more`.
- (k) Serve: a kind without its token header is `no_token` and no request reaches its fixture server. Mutation: build the provider anyway.
- (l) Leak test: distinctive tokens for all providers; tool results (text and structured) and captured logs contain none of them, and no title or author name appears in the logs.
- (m) A title containing `` ` ``, `<b>`, `[x](http://evil.example)` and `|` renders inside a code span and breaks neither the table nor X-30. Mutation: render the title as plain text.
