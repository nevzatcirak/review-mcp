# WP-24d: local-only configuration and local wording (2.10.0-rc.2)

Status: approved by the architect 2026-11-16. Package after V-20 (X-52, PR #71,
`2a721b8`); settles WP-24c DQ-1 and DQ-8 as decided on PR #71. Acceptance of
2.10.0-rc.1: issue #72 (36/36).

## Why

- **DQ-1.** A configuration with no git provider is refused ("no provider
  enabled: …"), so someone who only wants to review local work before pushing
  must invent a provider section that is never contacted. The command exits 1,
  and stdio starts degraded.
- **DQ-8.** Local output uses pull request words: the progress stage logs
  `fetching` although nothing is fetched, and the markdown heads with
  `## PR Review` and `Pull request: local — <subject>`.

## 0. Decisions

1. **Local-only configuration.** A configuration with no provider enabled is
   valid when `local.enabled` is true **and** the mode is stdio or the
   `local review` command. It stays invalid, with today's sentence, when:
   - `local.enabled` is false;
   - the mode is serve (local review does not exist there);
   - the command is `ci` or any `diag` subcommand that reads a pull request.
2. **No new key.** Local-only is derived (no provider enabled, `local.enabled`
   true); it is not a setting. `Config.LocalOnly() bool` is the one place that
   derives it.
3. **The tool set in local-only stdio** is exactly `server_info`,
   `local_review` and `job_result` (the latter as today, with background
   jobs). The prompt `multi_perspective_review` stays and accepts only
   `repo_path`; `review_linked_prs` is not registered.
4. **Wording.** In a local run:
   - the first progress stage is `reading` (not `fetching`), and the repository
     context stage is `reading repository context`;
   - the client markdown heads with `## Local review`;
   - the line under it is `Local work: <subject>`, or `Local work` when the
     subject is empty.

   The model prompt (the PR-Agent-derived template) is not changed in this
   package; see §5.
5. **Structured result unchanged** except one new field in `server_info`
   (§2.2). `pr.kind: "local"`, `pr.url: null` and the `local` object stay as in
   2.10.0-rc.1.

## 1. Configuration (commit 1: `feat(config): accept a local-only configuration`)

### 1.1 Validation

In `internal/config/validate.go`, the "no provider enabled" problem is raised
only when `serve` is true or `local.enabled` is false. The sentence itself does
not change.

`Config.LocalOnly()` returns true when no provider is enabled and
`local.enabled` is true. `Summary` lists no providers in that case (as today
for an empty list).

### 1.2 Commands that need a provider

Every entry point that reads a pull request calls one helper,
`config.RequireProvider(cfg) error`, right after the configuration loads. It
returns the **same** "no provider enabled: …" sentence when `cfg.LocalOnly()`
is true, as a `*config.ValidationError`. Callers keep their exit codes for an
invalid configuration:

- `review-mcp ci`: exit 1 (as for any invalid configuration in CI mode);
- `review-mcp diag <subcommand>` for every subcommand that builds a resolver or
  reads a pull request: the existing invalid-configuration exit code.

`diag` subcommands that read no pull request (for example a configuration
check, if one exists) must not call it. List every `diag` subcommand in the
report with "requires a provider: yes/no".

`review-mcp local review`, `version` and `help` never call it.

### 1.3 Startup log

In local-only stdio, the startup log line keeps `providers=[]`, and one more
info line follows: `no git provider is configured; only local reviews are available`.
Fixed words, no configuration content.

### 1.4 Tests and canaries

- **(n)** A configuration with only `llm.*` set loads without a problem and
  `LocalOnly()` is true. Mutation: raise the problem unconditionally again →
  the test fails.
- **(o)** The same configuration with `local.enabled = false` fails with
  today's sentence. Mutation: drop the `local.enabled` condition → fails.
- Serve validation with no provider fails with today's sentence (existing test
  extended or new).
- `ci` with a local-only configuration exits 1 and prints the sentence; no
  network call (the fake provider records none).

## 2. Stdio tool set (commit 2: `feat(mcpserver): local-only tool set`)

### 2.1 Registration

In `mcpserver.New`, when `deps.Config.LocalOnly()` (and not serve):
- register `server_info`, `local_review` and, with background jobs,
  `job_result`;
- register `multi_perspective_review`;
- register nothing else.

The degraded start (an invalid configuration) is unchanged: it still registers
the full set and reports `config_invalid`.

### 2.2 `server_info`

Add `local_only` (bool) to the structured output and its output schema; true
only in local-only mode. `status` stays `ok`.

### 2.3 Instructions

In local-only mode the server instructions are exactly this paragraph (plus
nothing else):

> review-mcp reviews local git work before it is pushed. No git provider is
> configured, so only local_review is available: it reads the commits after
> the merge base with the base and the uncommitted changes, and publishes
> nothing. Pull request tools appear once a provider (gitea, bitbucket_server,
> github or gitlab) is configured.

Write it as one constant; the docs quote it verbatim.

### 2.4 The prompt

`multi_perspective_review` with `pr_url` in local-only mode is refused with
`InvalidParams`:
`no git provider is configured; only local reviews are available (pass repo_path)`.
With `repo_path` it works as in rc.1.

### 2.5 Round trip and tests

- `npm/scripts/mcp-roundtrip.mjs`: if it asserts the tool set, it keeps the
  default (provider) configuration; add no local-only run unless it already
  parameterizes modes. State which in the report.
- **(p)** Local-only `tools/list` names exactly `job_result`, `local_review`,
  `server_info` (sorted). Mutation: register the full set → fails.
- A `local_review` call in local-only mode succeeds end to end against a fake
  LLM (no provider host anywhere in the environment).
- `server_info.local_only` true in local-only mode, false otherwise.
- The prompt refusal sentence, and its absence with a provider.

## 3. Wording (commit 3: `fix(review): local wording in progress and markdown`)

- `internal/review/pipeline.go`: add `StageReading = "reading"` and
  `StageRepoContextLocal = "reading repository context"`. A run with
  `Args.Local` reports these instead of `StageFetching` and `StageRepoContext`;
  the other stages are unchanged.
- `internal/review/render/client.go`: for `pr.Kind == "local"`, the heading is
  `## Local review` and the line is `Local work: <subject>` (subject through
  `mdutil.Inline`), or `Local work` when empty. No number, no URL. Everything
  after that line (focus, facts, findings, notes) is unchanged. The provider
  renderer is not used for local runs; do not change it.
- The CLI markdown uses the same renderer, so it changes with it.
- **(q)** Render test for a local result: heading and line. Mutation: the old
  `## PR Review` → fails.
- **(r)** A local run reports `reading` first, never `fetching`. Mutation:
  report `StageFetching` → fails.
- Existing pull request render goldens stay byte for byte.

## 5. Not in this package

- The model prompt's pull request words ("PR", "PR Info", "PR code diff") for
  local runs. It is the PR-Agent-derived template; changing it affects review
  quality and is measured by V-9 first. Backlog.
- Work-tree search for uncommitted files (backlog from WP-24b DQ-7).
- `pr_ask`/`pr_describe`/`pr_improve` on local work.
