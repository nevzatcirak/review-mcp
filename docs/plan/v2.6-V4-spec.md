## 1. WP-17a — the `ci` command (Opus)

### 1.1 Command and flags

`review-mcp ci <review|describe|improve> [flags]`. The command is stable: its flags, exit codes and output are documented and change only with a CHANGELOG entry. `diag` is unchanged.

| Flag | Commands | Meaning |
|---|---|---|
| `--pr-url URL` | all | The pull request. Wins over detection (§1.2). |
| `--publish` | all | Post the result (overview and inline comments; for describe, update the description as `pr_describe` does; for improve, post suggestions as `pr_improve` does). Without it, nothing is posted. |
| `--related URL` | review | Repeatable, at most 4; exactly the `related` argument (X-41). |
| `--focus NAME` | review | The `focus` argument; with `--publish` it is refused, as the tool refuses it. |
| `--incremental` | review | The `incremental` argument. |
| `--max-findings N`, `--output-language L` | review (and describe/improve where the tool has them) | As the tool arguments. |
| `--issue-context-file PATH` | review, describe | A JSON file with the shape of the `issue_context` argument (1–3 items). It is validated exactly as the argument is; an invalid file is a usage error (exit 2) naming the problem, never the file's content. |
| `--json` | all | Print the structured result instead of markdown. |
| `--fail-on LEVEL` | review | `security`, `any` or `issue-not-compliant` (§1.3). |
| `--fail-on-partial` | all | Exit 3 when the result's coverage is partial. |
| `--timeout D` | all | A Go duration (default `30m`, minimum `1m`) bounding the whole run. |

Every tool argument is validated by the tool's own `Validate`, so the CLI and the tools refuse the same things with the same messages.

### 1.2 Which pull request

1. `--pr-url` when given.
2. Otherwise, the pipeline's environment, only from these variables:
   - **Gitea Actions** (`GITEA_ACTIONS=true`): `{GITHUB_SERVER_URL}/{GITHUB_REPOSITORY}/pulls/{n}`.
   - **GitHub Actions** (`GITHUB_ACTIONS=true`, not Gitea): `{GITHUB_SERVER_URL}/{GITHUB_REPOSITORY}/pull/{n}`.
   - For both, `{n}` is `pull_request.number` from the JSON file at `GITHUB_EVENT_PATH`, only when `GITHUB_EVENT_NAME` is `pull_request` or `pull_request_target`. The file is read with a 1 MiB limit; only that one field is used.
   - **GitLab CI** (`GITLAB_CI=true`): `{CI_SERVER_URL}/{CI_MERGE_REQUEST_PROJECT_PATH}/-/merge_requests/{CI_MERGE_REQUEST_IID}`, only when `CI_MERGE_REQUEST_IID` is set (merge request pipelines).
3. Nothing else is read. Without a URL, the command exits 2 with: `no pull request: pass --pr-url (detected: <CI name or "none">)`.
4. The URL, given or detected, then goes through the configured resolver like a tool argument (pinned hosts; `url_not_configured` otherwise). It is logged only redacted, as the tools log it.
5. No token is read from CI variables (`GITHUB_TOKEN`, `CI_JOB_TOKEN`): only `REVIEW_MCP_*`.

### 1.3 Exit codes

| Code | When |
|---|---|
| `0` | Done: printed, and posted with `--publish`; also when coverage is partial or findings exist, unless a `--fail-on…` flag applies. |
| `1` | The run failed: configuration, provider, LLM, publish failure, or timeout. stderr carries the fixed error class (the same classes as the tools) and never a token. |
| `2` | Usage: unknown command or flag, invalid value, `--focus` with `--publish`, no pull request found, invalid issue context file. Nothing is loaded or sent before a usage error. |
| `3` | `--fail-on` met, or `--fail-on-partial` with partial coverage. The result is still printed and posted first. |

`--fail-on` levels:
- `security` means a key issue whose category is security, or the review's security concern field is set.
- `any` means at least one key issue.
- `issue-not-compliant` means the X-42 verdict is `not_compliant`.

Carried findings (X-36) count as findings of the run.

### 1.4 Output

- stdout: the markdown of `render.Client` (or JSON with `--json`), the same as `diag`.
- With `GITHUB_STEP_SUMMARY` set (GitHub and Gitea Actions), the markdown is also appended to that file. Write failures there are a warning, not an error.
- stderr: logs (level from the config), and one final line: `ci review: posted overview <id>`, `ci review: printed only (no --publish)`, or the error class.

### 1.5 Repository context and tools

Allowed, as in stdio. When `context.repo.cache_dir` is unset and `RUNNER_TEMP` is set, the cache goes to `$RUNNER_TEMP/review-mcp-repos`. The CI's own checkout is never read.

### 1.6 Tests and canaries

Tests:
- the detection table: each CI, the wrong event, a missing file, a file over 1 MiB, a missing number, and Gitea versus GitHub;
- `--pr-url` wins over detection;
- the exit-code table for each level, partial coverage and every usage error. A usage error must load nothing: assert that no config is read and no request is sent;
- the step summary is written and its failure is tolerated;
- the issue context file: valid, invalid, too many items;
- the timeout gives exit 1 with the timeout class;
- each command end to end on the existing fake provider and LLM, with and without `--publish`;
- no token in stdout, stderr or the step summary, using the existing leak assertions.

Canaries:
1. Detect a GitHub URL from a `push` event, and the detection test fails.
2. Return 0 when `--fail-on any` and a finding exist, and the exit test fails.
3. Read `GITHUB_TOKEN` as the provider token, and the credential test fails.

Commits:
1. `feat(ci): add the ci command`
2. `feat(ci): find the pull request of the pipeline`
3. `feat(ci): exit codes, fail-on and the step summary`

## 2. WP-17b — docs and examples (Sonnet)

- **`docs/ci.md`:**
  - what the command does and never does (R-1);
  - the flags and the exit-code table;
  - PR detection;
  - the token table per provider, with the minimal rights;
  - four examples:
    - GitHub Actions on `pull_request`, with `permissions: pull-requests: write, contents: read` and `REVIEW_MCP_GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`;
    - Gitea Actions;
    - a GitLab CI merge request job;
    - a generic shell step with `--pr-url`;
  - each example pins `@nevzatcirak/review-mcp@<version>` and uses `--publish` and `--incremental`;
  - a "Pull requests from forks" section: `pull_request` as the default, and `pull_request_target` as an opt-in with its two remaining risks (prompt injection steering the comment; the LLM key spent on anyone's pull request), and the fact that review-mcp never runs the pull request's code.
- **README:** one row in the tool table, "CI mode", linking to `docs/ci.md`.
- **Decisions doc:** X-46, with every settled DQ.

## 3. Acceptance (owner and architect, after the release)

- **Q1 — GitHub Actions.** A throwaway workflow on a throwaway branch of this repository, on `pull_request`. The PR is detected without `--pr-url`. With `--publish --incremental`, the overview is posted, and the step summary is written.
- **Q2 — incremental.** A second push to the same PR runs an incremental review.
- **Q3 — exit 3.** `--fail-on any` with a finding gives exit 3, and the job fails after posting.
- **Q4 — GitLab.** A merge request pipeline on the throwaway GitLab project detects the merge request and posts.
- **Q5 — no PR.** A `push` workflow without `--pr-url` exits 2 with the fixed message.
- **Q6 — generic.** A shell run with `--pr-url` on the owner's server.

The throwaway workflow file lives only on the fixture branch, never on `main`.
