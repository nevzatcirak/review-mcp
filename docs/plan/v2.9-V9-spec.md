## 0. Decisions

1. **Measure before changing** (owner). Every later quality item (V-18 impact trace, V-16 verification, V-17 samples) reports its delta against the baseline of this set, per variant, with the same model.
2. **Synthetic corpus, written from scratch** (architect). No code from any employer, customer or third-party repository. Each case is a small self-contained repository (a base tree and a head change) under `tools/evalset/corpus/`, MIT like the rest. Clean-room: generic names (`orders`, `billing`, `inventory`), placeholder hosts only.
3. **Neutral pull request text** (architect). Titles and descriptions say what the change does, never that it contains a defect ("Return early when the cart is empty", not "Bug: …"). The earlier acceptances showed that the PR text steers the model.
4. **Cascade cases are a first-class category** (owner). At least a third of the defect cases put the defect in an unchanged file, one or two calls away from the change.
5. **Clean cases** (architect). At least a quarter of the cases have nothing worth reporting. Findings on them are false positives, and "findings per clean pull request" is a headline metric.
6. **Gitea only for V-9** (architect). The architect can run a throwaway Gitea in its own container and the owner on the server; one provider keeps the variable count down. Other providers are not part of the score.
7. **Deterministic matching first, a judge second** (architect). A finding is matched to a ground-truth issue by fixed rules (§2.3). An optional LLM judge only re-examines what the rules left unmatched, it must use a different model from the reviewer, and its agreement with a human sample is reported.
8. **No telemetry, no upload** (architect). Everything stays under `-out`. Review text never goes to standard output or logs (as evalrepo).

## 1. WP-21a — the corpus (Opus)

Commit: `test(evalset): synthetic evaluation corpus`

### 1.1 Layout

```
tools/evalset/corpus/<case-id>/
  case.toml      # metadata and ground truth
  base/          # the repository at the base commit
  head/          # files added or changed by the pull request (overlay on base)
  deleted.txt    # optional: paths the pull request deletes, one per line
```

`case.toml`:

```toml
id = "java-cascade-signature"
language = "java"            # java | kotlin | typescript | go | python | csharp
category = "cascade"         # cascade | local | clean | security | concurrency
title = "Accept a currency in OrderRepository.save"
description = "Adds the currency to the stored order."

[[issue]]
id = "caller-not-updated"
severity = "high"            # high | medium | low
kind = "cascade"             # cascade (in an unchanged file) | local (in the diff)
path = "src/main/java/com/example/api/CheckoutController.java"
lines = [41, 44]
hops = 2                     # calls between the changed definition and the defect (cascade only)
must_mention = ["CheckoutController", "submit", "currency"]   # any of
summary = "CheckoutController.submit still calls save(order) through OrderService.persist; the currency is never passed, so every order is stored with the default."
```

A clean case has no `[[issue]]`.

### 1.2 Content (at least 24 cases)

| Category | Count | Must include |
|---|---|---|
| cascade | ≥ 8 | Java, Kotlin or C# (at least 3, with classes and interfaces), TypeScript, Go, Python. At least 4 with `hops = 2`. At least one of each: a changed signature with a caller two hops away that compiles but now behaves wrongly (an overload, a default value); a behaviour change without a signature change (null or an error where there was none, a unit change, an ordering change) relied on by a caller; an interface or abstract method change whose implementation in another package is not updated; an enum or constant value change used in a switch or comparison elsewhere. |
| local | ≥ 6 | Off-by-one, a missed error check, a wrong condition, resource not closed, wrong boundary, a copy-paste slip. |
| clean | ≥ 6 | A rename with every caller updated; a refactor that keeps behaviour; a docs-only change; a test-only change; a dependency-free extraction of a helper; a signature change with every caller updated two hops away (the clean twin of a cascade case). |
| security / concurrency | ≥ 4 | Injection through a caller, an authorization check bypassed by a new path, a data race on shared state, a missing lock on a changed path. |

Rules:
- Each base repository is small (5–40 files) but realistic: layers, an interface or two, tests, a README. Comments do not point at the defect.
- Each defect has exactly one ground-truth issue; a second real problem a reviewer may fairly find is either fixed or recorded as a `low` issue.
- Each cascade case has a clean twin where possible (same base, the callers updated), so the impact trace's false positives are measured.
- `lines` refer to the file at head (for an unchanged file, head equals base).
- `tools/evalset/corpus/README.md` lists every case with category, language, hops, and one line on what it tests. It contains no answers beyond `case.toml`.

### 1.3 Self-check (in WP-21a)

`go test ./tools/evalset/...` validates the corpus: every `case.toml` parses; categories and severities are known; every issue path exists at head; `lines` are inside the file; a cascade issue's path is not changed by the case; a clean case has no issue; ids are unique. Canary (c1): a case whose issue path is changed by its own head overlay must fail the check.

## 2. WP-21b — the tool (Sonnet)

Commits:
1. `feat(evalset): set up the corpus on a Gitea instance`
2. `feat(evalset): run variants and score them`

`tools/evalset` is a separate command, standard library only, not shipped. It shares nothing with the server at run time; it calls the built binary like evalrepo.

### 2.1 `evalset setup`

`go run ./tools/evalset setup -gitea-url URL -owner NAME [-prefix evalset-] -out DIR`
- The token is read from `EVALSET_GITEA_TOKEN` only (never a flag, never logged).
- For each case: create the repository `<prefix><case-id>` under the owner (or reuse it when it exists and its `main` matches the base tree hash; otherwise refuse and name the case); push the base to `main` and the head to `change`; open (or reuse) the pull request `change` → `main` with the case's title and description.
- Git runs with `-c core.hooksPath=/dev/null -c commit.gpgsign=false`, a fixed author (`evalset <evalset@example.com>`) and fixed dates, so trees and commit ids are reproducible.
- Writes `DIR/prs.json`: case id → pull request URL, base and head commit. Prints counts only.
- Refuses an `-out` that is not empty or lies inside the repository-context cache (evalrepo's rule).

### 2.2 `evalset run`

`go run ./tools/evalset run -bin ./review-mcp -prs DIR/prs.json -variants off,on [-repeat 1] -out DIR2`
- A variant is a named set of `diag review` flags, built in: `off` = `--repo-context=off`, `on` = `--repo-context=on`; V-18 adds `impact` = `--repo-context=on --impact=on`. A variant name that the binary does not support is refused before any run (probe `diag review --help`).
- For each case × variant × repeat: `review-mcp diag review --json <flags> <PR_URL>`; nothing is published. Stores `DIR2/<case>/<variant>-<n>.json` and the binary's version.
- Records per run: wall time, exit code, and from the result the coverage counts and model call counts where the result carries them (no new server fields in V-9).
- A failed run is recorded as failed and scored as "no answer" (counted separately, never as zero findings).

### 2.3 `evalset score`

`go run ./tools/evalset score -runs DIR2 -corpus tools/evalset/corpus [-judge] -out DIR3`

**Matching rules** (each finding matches at most one issue; each issue at most one finding per run; greedy by issue severity, then by line distance):
1. **Location:** the finding's path equals the issue path and its line (or range) overlaps `lines` widened by 3 on each side.
2. **Mention:** for a finding without a location in the issue's file (an overview-only finding, or one anchored on the changed definition): its text contains the issue file's base name or one of `must_mention` that is a code identifier, **and** at least one other `must_mention` entry. Matched case-sensitively on identifiers, case-insensitively on words.
3. A finding matched by neither is a **false positive candidate**.

**Judge (optional, `-judge`):** settings only from `EVALSET_JUDGE_BASE_URL`, `EVALSET_JUDGE_MODEL`, `EVALSET_JUDGE_API_KEY`. Refused when the judge model equals the reviewer model recorded in the run. For each false-positive candidate, the judge sees the case diff, the issue list and the finding, and answers one of `matches:<issue-id>`, `valid_unlisted`, `invalid`, with a one-line reason. `valid_unlisted` findings are counted separately (augmented precision, as ReviewBench does) and listed for the owner to add to the ground truth or reject.

**Human check:** `DIR3/sample.csv` holds a blind, seeded sample of 30 judged items (or all, if fewer) for the owner to label; `evalset agree -sample DIR3/sample.csv` reports judge-vs-human agreement. Until it is labeled, the report says "judge agreement not measured".

**Metrics** (per variant, mean and min–max over repeats):
- precision (matched findings ÷ all findings), augmented precision (with `valid_unlisted`), recall (matched issues ÷ issues), F1;
- severity-weighted recall (high 3, medium 2, low 1);
- **cascade recall** (cascade issues only) and recall by hops (1, 2);
- **findings per clean pull request** (mean; and the share of clean cases with zero findings);
- failed runs; wall time; model calls where known.

Outputs: `DIR3/report.md` (tables; no review text beyond finding titles), `DIR3/metrics.json`, `DIR3/matches.csv` (case, variant, repeat, finding title, issue id or `fp`, rule).

### 2.4 Tests and canaries (WP-21b)

- Scorer table tests: location match, ±3 widening, mention match needing two entries, one finding never matching two issues, a failed run is not zero findings, clean-case false positives.
- (c2) Mention rule requires two entries. Mutation: accept one; a test finding that only names the file must then wrongly match.
- (c3) Judge refused with the same model. Mutation: drop the check.
- (c4) Setup is reproducible: two setups of the same case give the same head commit id. Mutation: use the current time as the commit date.
- Leak test: a distinctive Gitea token and judge key never appear in any file under `-out` or in captured output.

## 3. WP-21c — the baseline (owner + architect)

- Instance: a throwaway Gitea (the architect's container or the owner's server). Binary: the 2.8.0 release (or the commit V-15 merges to). Model: the owner's usual review model; recorded by name class only in the repository ("OpenAI-compatible model A"), with the exact id kept outside the repository.
- Variants `off` and `on`, `-repeat 3`.
- Commit `docs(eval): baseline on 2.8` adds `docs/eval/baseline-2.8.md`: the metrics tables, the corpus commit, the binary version, the variants, repeats, judge agreement (or "not measured"), and the five most frequent false-positive patterns in one line each. No review text.
- This baseline is the reference for V-18 (`impact` variant) and V-16.

The baseline commit is the acceptance. Before it: the architect re-runs `evalset score` on the stored runs and gets the same numbers (determinism of the scorer), and spot-checks ten matches by hand.
