## 1. Problem

review-mcp's reviews are useful, but nothing measures them. The acceptances so far checked behaviour (anchoring, coverage notes, incremental runs), not whether findings are right. Acceptances recorded plausible but wrong statements (a misquoted consumer path; a CI job described as explained by the diff), and showed that the pull request's own text steers the model (a description saying "deliberate defects" led to no findings).

## 2. What the literature says (summary; sources in §6)

- **Precision is the bottleneck, not recall.** On a benchmark of 1,000 real pull requests with full repository context, every tool and model pairing had a low F1, mainly because of false positives; some pairings averaged several invalid comments per pull request. Feeding raw static-analysis output to the model without processing made precision worse, not better.
- **Agents told to find every issue get noisy.** A 2026 benchmark of code review agents reports a low signal-to-noise ratio for agents designed to surface all hidden issues.
- **A separate verification stage works in production.** An industrial system with a detection stage followed by a filtering stage reported 75% precision at large scale. Another, deployed on Bitbucket, checks each comment's factual consistency with the code with an LLM judge and drops vague, non-actionable comments with a classifier; its comments led to a code change in about 39% of cases, against about 44% for human comments.
- **The verifier should not be the producer.** A 2026 study found that a model asked to re-check its own output endorsed about a third of its own semantic errors.
- **Multiple independent reviews, merged, help.** Running the same review several times and merging the reports with one more model call raised F1 substantially on the benchmark above, because single runs catch different issues. Plain majority voting is a weaker signal: one non-peer-reviewed experiment suggests it rewards findings that recur, not findings that are right.
- **Longer critiques carry more nitpicks and hallucinations**, and the trade-off between coverage and precision can be tuned.
- **Adoption is the honest metric.** One industrial study measured whether a commented line changed afterwards ("outdated rate") as a scalable proxy for adoption. An evaluation set must also contain pull requests with nothing to find, so that restraint is measured.
- **Industrial deployment of a PR-Agent-based reviewer** (the project this one is inspired by) found most comments were acted on, but pull requests took longer to close, and practitioners named faulty suggestions as the main cost.
- **Numeric 1–10 scores from an LLM are inconsistent.** A categorical, evidence-backed verdict is preferred.

## 3. Plan

### V-9 — evaluation set and baseline (first)
- 20–30 pull requests: synthetic fixtures plus permissively licensed public repositories; at least a quarter with nothing worth reporting. Ground truth per pull request: the issues a careful reviewer must find, with file and line.
- Metrics: precision, recall, findings per clean pull request (false positives where silence is right), severity-weighted recall, cost (calls, tokens, seconds).
- An LLM judge matches findings to ground truth; its agreement with a human labeling of a sample is reported, and the judge model differs from the reviewing model.
- Baseline: 2.7/2.8 as released. Every later change reports its delta against it. Lives under `tools/` (offline), never in the server.

### V-16 — verification stage
- After the review call, each candidate finding is checked by a second call: does the quoted evidence exist in the diff or the context sent, is the claim consistent with the code, is it actionable. Verdict `keep`, `drop` or `downgrade`.
- Optional separate model (`llm.verifier_model`, defaulting to the primary), reusing the X-38 chain machinery and the X-37 limiter.
- Honesty: the number of dropped findings is a structured count and a note; a verifier failure keeps the findings and says so (never a silent drop, never a silent keep).
- Prompt side, shipped with it: every finding quotes its evidence line; "no findings" is a valid answer; a cap on style-only findings.

### V-17 — multi-sample aggregation
- `review.samples` (default 1): n independent review calls, merged as a union, then verified (V-16). Opt-in, because it costs n calls; subject to the limiter. `multi_perspective_review` stays the focused variant of the same idea.

## 4. Non-goals
- No fine-tuned model and no telemetry-based feedback loop: review-mcp has no telemetry. The "outdated rate" is computed offline in V-9 from public pull requests and, optionally, by a user locally from the incremental records (X-36).
- No numeric review score.

## 5. Planned, not yet specified
- **`scope` focus.** A seventh focus for pull requests written with coding agents: changes outside the stated purpose, speculative abstractions, changes without a way to verify them (no test, no success criterion). The idea follows the widely shared coding guidelines distilled from Andrej Karpathy's remarks on LLM coding pitfalls; the prompt text is written from scratch and the docs name the inspiration.
- **Client skill file.** A `SKILL.md` shipped with the npm package and the docs that teaches an MCP client the workflow: list review requests (V-15) → `pr_info` → `pr_review` (focused runs, merged publish) → optional `pr_review_decision`. Client-side only; the server is unchanged.
