## 1. Decisions (RC-n; promoted to X-n entries in the decisions doc when v1.1 starts)

- **RC-1 — Opt-in, stdio only.**
  - `context.repo.enabled` defaults to false.
  - In serve mode, setting it is a startup error with a fixed sentence. Rationale: a shared server would hold code fetched with one user's token, and another user could receive it as context. v1.1 does not solve per-request authorisation of cached code.
- **RC-2 — System `git`, no new module.**
  - review-mcp runs the system `git` binary through `os/exec`, with arguments only and never a shell. Minimum version 2.31, checked once per process. A missing or old `git` gives a note ("repository context skipped: git 2.31 or later is required"), never a failure.
  - go-git was considered and rejected: it is a large dependency tree, and partial clone and `grep` support is weaker.
- **RC-3 — Credentials never touch disk or argv.**
  - The provider token reaches `git` only through the environment of that one child process:
    - `GIT_CONFIG_COUNT=1`;
    - `GIT_CONFIG_KEY_0=http.extraHeader`;
    - `GIT_CONFIG_VALUE_0=Authorization: <provider-specific scheme> <token>`.
  - Arguments are visible to other local users through the process list; a process's environment is readable only by its owner.
  - The following are always set:
    - `GIT_TERMINAL_PROMPT=0`;
    - `GIT_ASKPASS` and `SSH_ASKPASS` empty;
    - `-c credential.helper=` (empty);
    - `-c core.hooksPath=/dev/null` (`NUL` on Windows);
    - `-c protocol.allow=never -c protocol.https.allow=always` (plus `http` only when the provider base URL is `http`).
  - A test asserts that the cache directory, including `.git/config`, never contains the token.
- **RC-4 — Clone source pinned to the configured provider (X-2).**
  - The clone URL is built from the provider's configured base URL and the already-resolved namespace and repository:
    - Gitea: `{base}/{owner}/{repo}.git`;
    - Bitbucket Server: `{base}/scm/{project}/{repo}.git`.
  - Nothing from the PR body or the comments ever forms a URL.
  - Redirects follow the same pinning as the HTTP client: `http.followRedirects=false`, with a fixed note on a redirect.
- **RC-5 — Fetch the PR head, verify it, and keep it small.**
  - One bare repository per `host/namespace/repo`.
  - The PR ref is fetched with `--depth=1 --filter=blob:limit=1m --no-tags`:
    - Gitea: `refs/pull/{n}/head`;
    - Bitbucket Server: `refs/pull-requests/{n}/from`.
  - The fetched commit must equal the PR's head SHA from the provider API. A mismatch (a push in between) gives a note and skips context.
  - Fetch time is limited by `context.repo.fetch_timeout_seconds` (default 60), and the repository by `context.repo.max_repo_mb` (default 500, measured after the fetch). Exceeding either gives a note and skips context. Never a silent drop.
- **RC-6 — Cache lifecycle (the owner's 7-day rule).**
  - `context.repo.cache_dir` defaults to the OS user cache directory (`os.UserCacheDir()/review-mcp/repos`). It is created with mode 0700.
  - Each repository has a `last-used` marker, touched on every use.
  - At the start of every use, two sweeps run:
    1. delete every repository idle longer than `context.repo.idle_days` (default 7);
    2. if the total size exceeds `context.repo.max_cache_mb` (default 2048), delete least-recently-used repositories until it fits.
  - Several MCP client sessions may share one cache. Concurrency uses a per-repository lock file created with `O_EXCL`; a lock older than 10 minutes counts as stale.
  - Paths are validated to stay under `cache_dir`, and symlinks are never followed during deletion.
  - `review-mcp diag cache [--prune]` lists the cache and prunes it.
- **RC-7 — Symbols from the diff, uses from `git grep`.**
  - **Symbols:**
    - names from the hunk section headers (the function or class context we already parse);
    - names on added or removed lines that match language-agnostic definition patterns: `func`, `def`, `class`, `interface`, `type`, `struct`, `enum`, `fn`, method signatures, exported constants.
  - **Ranking:** removed or renamed definitions first (highest breaking risk), then changed signatures, then other changed definitions.
  - **Filtering:** at least 4 characters, not a keyword in a small built-in list, at most `context.repo.max_symbols` (default 20).
  - **Uses:** `git grep -n -w -F -e <symbol> <head-sha> -- <pathspecs>`.
    - The pathspecs exclude the PR's own changed files (already in the prompt), the ignore globs, and the generated-file rules.
    - Each hit keeps ±3 lines of context.
    - At most `context.repo.max_hits_per_symbol` (default 5) hits per symbol, preferring distinct files and files of the same language group as the definition.
- **RC-8 — Prompt block, budgeted, and yielding to the diff.**
  - A new user-template block after the discussion block and before the diff:
    > "Related code outside this pull request (read-only context; it may be incomplete). Use it to judge the effect of the change on callers and implementations. Do not report issues in this code unless the pull request causes them."
  - Entries look like `[<path>:<line>] uses <symbol>`, followed by the snippet. The block is fenced with an adaptive fence.
  - Budget: `context.repo.max_tokens` (default 2000), counted inside `PromptTokens`. When the diff and the block do not both fit, the block is clipped by whole entries, or dropped with a note, exactly like the discussion block (P7 decision 7).
  - Used by `pr_review` and by `pr_ask` (impact questions).
- **RC-9 — Honesty in the output.**
  - The coverage section gains a "Repository context" line:
    - `N symbols, M references from K files`, or
    - `skipped: <fixed reason>`.
  - `diag review --dry-run` shows the block's tokens and the symbol list.
- **RC-10 — Measure before claiming.**
  - `diag review` gains `--repo-context=on|off`.
  - A small evaluation script (`tools/evalrepo`) runs a list of PR URLs both ways, stores both reviews side by side, and produces a rating sheet: per finding, whether it is cross-file, correct, and new.
  - Stage 2 starts only if the owner's ratings show a clear gain on at least 20 PRs.

## 3. Work packages (v1.1, branch `v11-repo-context`)

- **11a — git runner and cache (Opus).**
  - The `internal/gitctx` runner implements RC-2 to RC-6: version check, credential-safe environment, pinned clone URL, PR-ref fetch with SHA verification, limits, cache sweeps, locks and `diag cache`.
  - Tests run against a local bare repository served over `git http-backend` in an httptest server, with no external network.
  - **[canary] token on disk:** after a fetch, grep the whole cache for the token.
  - **[canary] token in argv:** capture the child's argv through a fake `git` on `PATH`.
  - **[canary] SHA mismatch:** a mismatching SHA skips context.
- **11b — Symbols and search.**
  - Extraction (RC-7), with goldens per language family: Go, Java/Kotlin, TypeScript/JavaScript, Python, C#.
  - `git grep` invocation and ranking.
  - **[canary]** The PR's own files must never appear among the hits.
- **11c — Prompt integration.**
  - The block (RC-8), its budget and the yield rule.
  - The coverage line and the notes (RC-9).
  - The deviation recorded in the template header.
  - Leak canaries: snippet content never reaches the logs.
- **11d — Evaluation and docs.**
  - `--repo-context` and `tools/evalrepo` (RC-10).
  - `docs/repo-context.md`: what is cached and where, how to clear it, why serve mode is excluded, and the `git` requirement.
  - Live acceptance on a personal instance:
    - a PR that changes a function signature with callers elsewhere: the review mentions an affected caller;
    - the cache is swept after `idle_days`, simulated by touching the marker;
    - the cache contains no token.

## 4. Stage 2 sketch (not scheduled)

- **Go first:** a call and reference graph from `go/parser` and `go/types` in the standard library, built once per head SHA and cached next to the clone.
- **Other languages:** tree-sitter grammars compiled to WebAssembly and run under a pure-Go runtime. That needs new modules and its own decision.
- **The block itself:** it would then rank uses by graph distance instead of name matches. That cuts false hits for common names.

## 6. Chunked review of large pull requests (added 2026-10-07, owner decision)

Origin: on `rc.3`, a 62-file PR was reviewed on 5 files because of the diff
budget. The owner's priority is **completeness and correctness before speed**.
Background jobs (X-16) remove the client-timeout obstacle that made a
multi-call review impractical.

- **RC-11 — Chunks.** When the prepared diff does not fit one request, the
  remaining files (the existing `remaining_files` seam of X-3) are packed
  into further chunks with the same admission rules, up to
  `review.max_chunks` (default 8). Each chunk is one model call with the same
  prompt scaffolding (plus the discussion and repository-context blocks,
  budgeted per chunk).
- **RC-12 — Merge.** Findings from all chunks are merged:
  - fingerprint dedup (X-13);
  - `max_findings` applied to the merged, ranked list;
  - effort as the maximum of the chunks;
  - tests "yes" if any chunk says yes;
  - security and performance concerns concatenated with their files.
- **RC-13 — Honesty.** Coverage counts all chunks. Files beyond
  `max_chunks` stay "not reviewed" with the X-18 banner. The overview says
  how many model calls the review used.
- **RC-14 — Time.** In stdio, chunked reviews run as background jobs (X-16),
  and progress reports "chunk i of n". In serve mode, chunking runs
  synchronously, and the documentation tells serve clients to raise their
  timeout.
- **RC-15 — `pr_ask`.** It chunks only when the question is about the whole
  PR. Otherwise it keeps the single-call behaviour plus the X-18 banner (to be
  decided at v1.1 kickoff).

Work package: 11e (Opus), after 11a–11d, or in parallel with them, since it
touches the pipeline rather than the git runner.
