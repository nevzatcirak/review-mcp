## 0. Decisions

- **X-36 — Incremental review (V-1).** `pr_review` can review only the files of the pull request whose content changed since the last review review-mcp published on it. The overview records the head commit it reviewed; the next incremental run compares every file of the current diff between that commit and the current head **by content**, so rebases and force-pushes need no special case. Unchanged files are not sent to the model and are reported as such. Nothing is built or run (R-1).

**Merge rule.** v2.1 work does not reach `main` before `v2.0.0` is tagged. The PR stays draft and unmerged until then. If a 2.0 fix is needed meanwhile, it goes to `main` as before; v2.1 rebases on it.

**Owner defaults (approved 2026-10-14):**

1. `review.incremental` defaults to **false**: behaviour is unchanged unless the user turns it on (config) or passes `incremental=true`.
2. API change detection reads at most **300 files** (`review.incremental_max_files`); a larger pull request gets a full review with a note.
3. An incremental overview **does not carry forward** earlier findings; it states its scope (which commit it continues from, how many files it skipped) and that earlier inline comments stay on the pull request. Carrying earlier overview-only findings forward is backlog.
4. Scope: **`pr_review` only.** `pr_improve` and `pr_describe` stay full; they may follow later with the same detection.

## 1. WP-7a — Housekeeping (Sonnet)

Four backlog items, each its own commit, no behaviour change outside what is named.

1. **`Diff.Incomplete`** (provider-neutral). A provider sets it when the host stopped listing changed files (GitHub's 3000-file cap; GitLab's diff limit and the 40-page cap). Coverage honours it: `partial` is true and the existing note stays. Contract: a case where the fake stops listing gives `Incomplete` and partial coverage on every provider that can (others declare it impossible through a trait). **[canary]** ignore `Incomplete` in coverage: the case fails.
   Commit: `feat(provider): mark a diff the host did not list completely`
2. **`commit_messages` contract case.** Every provider returns its commit messages oldest first; the fake serves them in the host's own order (GitLab newest first). **[canary]** drop GitLab's reversal: the shared case fails for GitLab only.
   Commit: `test(contract): check the order of commit messages on every provider`
3. **One place for the line type.** `improve.anchorFor` is folded into `internal/review/anchor` (for example `anchor.ResolveExact`), so the line type and `OldLine` are computed in one function. No behaviour change: every golden and contract test passes unchanged. If the two callers truly need different rules, write a DESIGN-QUESTION instead of merging them.
   Commit: `refactor(anchor): compute line types in one place`
4. **Code spans inside the GFM `<summary>`.** Markdown is not rendered inside `<summary>`, so a finding header with `` `name` `` shows backticks. Inside `<summary>` the renderer emits each well-formed code span (X-30) as `<code>…</code>` with HTML escaping of its content; everything else is escaped as today. Golden files for Gitea, GitHub and GitLab GFM change accordingly; Bitbucket Server (no `<summary>`) is unchanged. **[canary]** keep backticks inside `<summary>`: the golden test fails.
   Commit: `fix(review): render code spans in collapsible headers as HTML code`

## 2. WP-7b — The reviewed-commit record (Sonnet)

1. **Record.** Every overview review-mcp publishes (a full or an incremental `pr_review` publish) gets a hidden line directly above the overview marker: `[//]: # (review-mcp:reviewed:<head sha>)`, the head commit the run reviewed (`PullRequest.HeadSHA` of the run, 40 or 64 lowercase hex). It is a CommonMark link reference definition like the marker and renders as nothing.
2. **Visible line.** The overview's footer gains a renderer-built line: "Reviewed commit: `abc1234`" (short form, 7 characters), and for an incremental run "Reviewed commit: `abc1234` (changes since `def5678`)". Provider renderers and the client renderer.
3. **Read.** `findOverview` (X-12) returns, next to the comment, the reviewed SHA parsed from **the own overview only** (author check as today). A line that is not exactly the format (wrong length, upper case, extra text) is ignored: no SHA. Several such lines: the last one above the marker wins.
4. **Merged publish (X-33).** A `findings` publish carries the previous reviewed SHA over unchanged (or writes none when there was none): the client's focused runs may have reviewed an older head, and recording the current head would let an incremental run skip files no model saw.
5. **Tests:** the line round-trips; a planted line in someone else's comment is never read; a malformed line is ignored; the merged publish keeps the old SHA. **[canary]** read the SHA from any general comment: the planted-line case fails. **[canary]** write the current head on a merged publish: the carry-over case fails.

Commit: `feat(review): record the reviewed commit in the overview`

## 3. WP-7c — Change detection (Opus)

`internal/review/incremental` (new): given the current diff, the current head and the last reviewed SHA, it returns, for every **listed** file of the diff, `changed` or `unchanged`, plus the strategy used and notes. Read-only.

1. **Local strategy (`git`)**, used when X-22 repository context is enabled and its checkout holds both commits (`HasCommit` for each): a new read-only `gitctx` method `ChangedPaths(ctx, c, from, to)` runs `git diff --name-only -z --no-renames --no-ext-diff --no-textconv <from> <to>` in the checkout (no hooks, no repository configuration executed, same environment rules as the other `gitctx` commands). A file of the diff is `changed` when its path or its old path is in the output. Strategy `git:diff`.
2. **API strategy**, otherwise: for each listed file, the content at the last reviewed SHA (`GetFileAt(path, last)`) is compared with the content at the head (the diff's head content when it was fetched in full, else `GetFileAt(path, head)`); equal bytes → `unchanged`; any difference, a `not_found` on exactly one side, a `too_large` or any other error → `changed` (never skip a file on doubt). A deleted file is `unchanged` only when it is also absent at the last SHA. At most `review.incremental_max_files` files (default 300); above that, no comparison is made and the run is full with a note. Reads run with the concurrency the providers already use for contents. Strategy `api:contents`.
3. **Unusable last SHA.** Before any per-file read, the commit must be readable: `HasCommit` (local) or `ListDir("", last)` (API) — `not_found` means the commit is gone (for example after a force-push and garbage collection): full review with a note. Any other error: full review with a note.
4. **Notes (fixed sentences):**
   - "The commit of the last review is no longer available, so the whole pull request was reviewed."
   - "The last review could not be compared with the current head, so the whole pull request was reviewed."
   - "The pull request has more than N files, so it was not compared with the last review and was reviewed in full."
5. **Tests:** both strategies on fixtures with an unchanged file, an edited file, a file reverted to its earlier content (unchanged), a rename since the last review (changed), a deletion, a file too large, a read error (changed), a force-push where the old commit still exists (content decides), a gone commit (full). The local strategy against a real `git` repository in a temp directory. **[canary]** treat a read error as unchanged: the read-error case fails. **[canary]** pass `--textconv` (or drop `--no-ext-diff`): the argv test fails.

Commit: `feat(review): find the files that changed since the last review`

## 4. WP-7d — The incremental pipeline (Opus)

1. **Switches.** Config `review.incremental` (bool, `REVIEW_MCP_REVIEW_INCREMENTAL`, default per §0) and `review.incremental_max_files` (int, default 300, 1–5000). `pr_review` argument `incremental` (bool, optional) replaces the config for the call. `server_info` shows both settings.
2. **Flow** (after the PR read, before the prompt is built):
   - No own overview or no valid reviewed SHA → full review; when incremental was requested explicitly (argument `true`), the note "No earlier review by review-mcp was found on this pull request, so the whole pull request was reviewed."
   - Reviewed SHA equals the current head → **no model call**: result with the note "Nothing changed since the last review (commit `abc1234`); nothing was reviewed." With `publish=true` nothing is posted or edited.
   - Otherwise run WP-7c. All listed files unchanged → no model call, the note "No file of the pull request changed since the last review (commit `abc1234`); nothing was reviewed.", nothing posted. Some changed → the diff given to the prompt pipeline holds only the changed files (their full PR patches, base to head, so the model sees the whole change of each file); unchanged files never reach the model.
   - A full fallback from WP-7c reviews everything and carries WP-7c's note.
3. **Prompt.** One fixed sentence in the system prompt when the run is incremental: "This is an incremental review: only the files that changed since the last review are shown; findings already posted on the pull request were not repeated." No other prompt change.
4. **Coverage and result.**
   - Unchanged files are listed in `coverage.skipped` with the new reason `unchanged_since_review`; they do **not** make coverage partial and are not counted in `not_reviewed_files`; a new count `unchanged_files`.
   - Result gains `incremental`: `mode` (`full`, `incremental`, `unchanged`), `since` (the last reviewed SHA, when one was used), `strategy` (`git:diff`, `api:contents`, or empty), `changed_files`, `unchanged_files`. Schema updated (optional fields, always set by the tool).
   - The overview's existing coverage line says "N files reviewed, M unchanged since the last review" for an incremental run.
5. **Interplay.**
   - `focus` runs may be incremental (they never publish, so they never write a SHA).
   - A `findings` publish never computes changes (no model call) and carries the SHA over (WP-7b item 4).
   - X-19 parts, X-29 duplicates, X-31 CI, X-32 guidelines and file tree work on the reduced diff unchanged; the file tree covers the directories of the changed files only.
6. **Tests:** the three modes through `review.Run` on one provider fake and on the contract review harness for every provider (a second run after a head change touching one of two files reviews one file and posts only for it; a run on the same head makes no model call); the explicit-request note; the max-files fallback; coverage counts. **[canary]** send unchanged files to the model: the one-file case fails (the fake LLM sees two files). **[canary]** count unchanged files as not reviewed: the coverage case fails (`partial` true).

Commit: `feat(review): review only the files that changed since the last review`

## 5. WP-7e — Docs, decisions and acceptance (Sonnet)

- `docs/review.md` (incremental section: switches, the three modes, the record line, what is not carried forward, the strategies and their costs), `docs/troubleshooting.md` (every new note verbatim), `docs/setup.md` (config keys), README tool notes, NOTICE/README attribution line for the PR-Agent idea.
- Decisions doc: X-36 row and section with every settled DQ. CHANGELOG `## [2.1.0-rc.1] - Unreleased`.
- **Acceptance (owner, after the release, on a throwaway PR in this repository):**
  - **Q1** full review with `publish=true`; the overview shows "Reviewed commit".
  - **Q2** push one commit touching one of two changed files; `pr_review` with `incremental=true` reviews one file, `incremental.mode` is `incremental`, the overview says "changes since …", nothing is posted for the other file.
  - **Q3** run again without a new commit: `mode` `unchanged`, no model call (`llm_calls` 0), nothing posted.
  - **Q4** force-push a rebased branch: the content comparison decides (files whose content did not change stay unchanged).
  - **Q5** without repository context: strategy `api:contents`. With repository context enabled, `git:diff` appears only when this run fetched the head **and** the cache still holds the last reviewed commit from an earlier run (settled WP-7d DQ-1); otherwise `api:contents` is correct. Record which one was seen.
  - **Q6** a review that is partial (a part failed or the budget left files out) records no reviewed commit, so the next incremental run is full (settled WP-7d DQ-3).

Commit: `docs: document incremental review`
