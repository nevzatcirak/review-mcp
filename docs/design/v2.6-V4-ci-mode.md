## 1. Problem

Today review-mcp runs only inside an MCP client: `stdio` for one user, and `serve` for many users with their own tokens. A team that wants every pull request reviewed automatically, with nobody calling a tool, has two options:
- drive `diag review --publish` from a script, which is a diagnostic command with diagnostic flags and output;
- write its own MCP client.

Neither is supported or documented for that use.

CI mode makes this a supported use. A pipeline step runs one command for the pull request that triggered it, with the CI's secrets. The command posts the same overview and inline comments as `pr_review` and exits with a meaningful status. As everywhere else, the code under review is never built or run (R-1).

## 2. What is already there

- **`diag review | describe | improve | ask`** run the same pipelines as the tools from the command line. They have `--publish`, `--json` and `--repo-context`. They are diagnostic: the flags and the output format are not a stable interface.
- **Configuration** comes entirely from environment variables (`REVIEW_MCP_*`) or a TOML file. Both fit CI secrets.
- **Incremental review (X-36)** already suits pipelines, which run again on every push.
- **The output paths:** the published overview (edited in place), inline comments, `job_result` for slow endpoints, and the structured result.
- **Repository context (X-22)** is allowed in stdio. A CI job is one process for one user, so it is the same trust situation.

## 3. Decisions for the owner

Each item gives a recommendation and its alternative.

1. **Command.** A new stable subcommand: `review-mcp ci <review|describe|improve>`. It is not `diag`, which stays diagnostic, and it has no `ask`, because a pipeline has no one to ask a question.
   - Flags mirror the tool arguments: `--pr-url`, `--related URL` (repeatable), `--focus`, `--incremental`, `--publish`, `--output-language`, `--max-findings`, `--json`.
   - The flag names and exit codes are a documented, versioned interface.
   - *Alternative:* promote `diag review` to stable. Not recommended, because it would freeze the diagnostic flags.

2. **Which pull request.** `--pr-url` always wins. Without it, the command reads the pipeline's own environment, only from these known variables:
   - **GitHub Actions and Gitea Actions** (the same variables): `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY`, and the pull request number from the event file `GITHUB_EVENT_PATH` (`pull_request.number`), for `pull_request` and `pull_request_target` events.
   - **GitLab CI:** `CI_SERVER_URL`, `CI_MERGE_REQUEST_PROJECT_PATH` and `CI_MERGE_REQUEST_IID`, in merge request pipelines only.
   - **Anything else** (Jenkins, Bamboo, Bitbucket Server, other runners): `--pr-url` is required, with a fixed error that names the flag.

   The detected URL then goes through the same resolver and host pinning as a tool argument. A pipeline cannot make review-mcp send a token to a host that is not configured. Nothing is guessed from a branch name or a commit message.

3. **Publishing default.** `--publish` must be given explicitly. Without it, the review is printed and nothing is posted. The examples always pass it.
   - *Reason:* a first run in a new pipeline should be safe to try.
   - *Alternative:* publish by default in CI.

4. **Exit codes.** These are part of the interface:
   - `0`: done; the review was printed or published, even when coverage is partial or the review found issues;
   - `1`: the run failed (provider, LLM or configuration error), with the fixed error class on stderr;
   - `2`: usage error;
   - `3`: only with `--fail-on <level>`, where findings met that level.

   Levels: `security` (a security finding), `any` (any key issue), and `issue-not-compliant` (X-42 verdict `not_compliant`). The default is advisory: never fail on findings.
   - *Reason:* a reviewer model is not a gate by default. A team opts in.

5. **Partial coverage in CI.** A partial review still exits 0, and the notes are printed and published as today (X-18). `--fail-on-partial` makes it exit 3. It is off by default.

6. **Output.**
   - **stdout:** the review as markdown, or the structured result with `--json`.
   - **stderr:** logs only, never a token (as everywhere).
   - **GitHub and Gitea Actions:** when `GITHUB_STEP_SUMMARY` is set, the markdown is also appended there.
   - **GitLab CI:** none; the output stays on stdout.

   No annotations or check runs in V-4; check runs would need a GitHub App. Backlog.

7. **Credentials.** The same `REVIEW_MCP_*` variables, from the CI's secrets. The docs show the minimal token per provider:
   - **GitHub Actions:** the job's `GITHUB_TOKEN`, with `permissions: pull-requests: write, contents: read`, passed as `REVIEW_MCP_GITHUB_TOKEN`;
   - **GitLab:** a project or group access token with `api` (reading and posting notes);
   - **Gitea:** a token with repository read and issue write;
   - **Bitbucket Server:** an HTTP access token with repository read and pull request comment rights.

   review-mcp never reads `GITHUB_TOKEN` or `CI_JOB_TOKEN` on its own: the mapping is explicit in the pipeline.

8. **Untrusted pull requests (fork PRs).** Secrets are not given to `pull_request` runs from forks on GitHub. `pull_request_target` gives them, while running the base branch's workflow.
   - review-mcp never checks out or runs PR code (R-1), so the classic `pull_request_target` risk (running the fork's code with secrets) does not apply.
   - Two risks remain:
     - the PR text and diff reach the LLM, where a prompt injection can steer the published comment;
     - the LLM key is spent on anyone's PR.
   - *Recommendation:* the docs show `pull_request` for same-repository PRs as the default, and `pull_request_target` as an opt-in with these two risks stated plainly. There is no code switch either way: the trigger is the pipeline owner's choice.

9. **Repository context and tools in CI.** These are allowed (stdio rules). The cache goes in a runner-local directory, `RUNNER_TEMP`, or `context.repo.cache_dir` when set. The CI's own checkout is not used: X-22 fetches its own pinned head with its own isolation, and the CI checkout may hold build output or a different commit.

10. **Issue context without a client (V-3).** `--issue-context-file path.json` takes the same shape as the `issue_context` tool argument. An earlier pipeline step can write it from any tracker, by its own means. Still no built-in tracker client: review-mcp never contacts trackers (X-42 holds).

11. **Timeouts and slow endpoints.**
    - `--timeout` (default 30 minutes) bounds the whole run.
    - The X-37 rate limiter and the X-38 fallbacks apply unchanged.
    - There is no `job_result` in CI: the command waits for the result itself.

12. **Examples shipped in `docs/ci.md`:** a GitHub Actions workflow, a Gitea Actions workflow, a GitLab CI job, and a generic shell step for Jenkins or Bitbucket. Each runs `npx -y @nevzatcirak/review-mcp@<version> ci review --publish …`. V-7 adds a container image line later. No marketplace Action in V-4 (backlog: a composite Action that wraps the same command).

## 4. Out of scope for V-4

- Check runs, annotations or status checks (they need a GitHub App or per-provider APIs; backlog).
- Running on push events without a pull request.
- Any built-in tracker client.
- Anything that builds, tests or loads repository code (R-1).
