# v2.5.x — WP-14: every changed file reaches the review (file limit)

| | |
|---|---|
| Status | Approved by the owner 2026-10-20 (A first, then B; both as 2.5.x packages after V-13b) |
| Origin | In-use report: a Bitbucket Server pull request with 118 changed files was reviewed on 50 files. The other 68 were skipped as `file_limit` by `diff.max_files_full_content` (default 50), before any chunking, and the key that controls it is not in the user-facing configuration docs. |
| Binding inputs | DQ-19 (Bitbucket Server diff acquisition), DQ-20 (base SHA), X-18 (partial-coverage honesty), X-19 (review in parts), R-1 |
| Packages | **Part A:** WP-14a (Sonnet). **Part B:** WP-14b (Opus), WP-14c (Sonnet). |
| Release | Part A: `2.5.1` (2.5.0 is stable since 2026-10-20). Part B: the next release after Part A. |

---

## 0. Owner decisions (approved 2026-10-20)

1. **Part A, quick fix:** raise the default of `diff.max_files_full_content` from 50 to **300**, document every `diff.*` key, and make a result that lost files to that key name the key.
2. **Part B, structural fix:** on Bitbucket Server, files beyond `diff.max_files_full_content` are no longer skipped. Their patch comes from Bitbucket's own diff endpoint, at the pinned base and head commits, and they are marked "contents not fetched", exactly like the other three providers. Decision **X-44** amends DQ-19.
3. Files within the limit keep today's path (base and head contents, local diff). Their patches stay byte-identical.
4. A file whose native diff Bitbucket truncates is never shown in part: it is skipped as `size_limit`.

### A.2 `feat(review): name the file limit when it skipped files`
- `internal/llmrun/notes.go`: add
  `NoteFileLimitFormat = "%s skipped because of diff.max_files_full_content; raise it to review them."`
  (argument: the existing `CountPhrase` of the number of `file_limit` skips, e.g. "68 files").
- `ChunkedPartialNotes` (and therefore `PartialNotes`): when at least one skip has reason `file_limit`, add `NoteFileLimitFormat`. `NoteProviderSkips` is added only when a skip with **another** reason that loses a reviewable file exists (`size_limit`, `fetch_failed`, `unparseable_patch`, unknown), so a result that lost files only to the file limit carries the new note and not the generic one.
- Order: budget hint (unchanged), then `NoteFileLimitFormat`, then `NoteProviderSkips`.
- Every tool that calls these functions (`pr_review`, `pr_describe`, `pr_improve`, `pr_ask`, focused runs, merged publish) gets the note with no further change. Check each one with a test; list them in the report.
- The note appears in the tool text, the structured `notes`, and the published overview, like every other X-18 note.
- Tests:
  - **[canary]** only `file_limit` skips → the new note with the right count, no `NoteProviderSkips`. Mutation: drop the `file_limit` branch; the test must fail.
  - **[canary]** `file_limit` plus `fetch_failed` → both notes, in the order above. Mutation: emit `NoteProviderSkips` only when no `file_limit` skip exists; the test must fail.
  - A chunked review with `file_limit` skips and parts left out → budget hint and the new note.
- Goldens that contain `file_limit` change on purpose; list each changed golden in the report with a one-line reason.

### A.3 `docs: document the diff limits`
- `docs/setup.md`: a new section "Diff limits" with a table of every `diff.*` key in the §5 table (key, environment variable, default, range, meaning), including at least `diff.max_files_full_content`, `diff.max_file_bytes`, `diff.max_diff_bytes`, `diff.large_patch_policy`, `diff.max_tokens`, `diff.extra_lines_before`, `diff.extra_lines_after`, `diff.skip_extend_extensions`, `diff.max_description_tokens`, `diff.max_commits_tokens`. Cross-check against `internal/config/table.go` line by line; report any key in the table that is still undocumented anywhere.
- The meaning of `diff.max_files_full_content` says, per provider:
  - Gitea, GitHub, GitLab: files beyond the limit are reviewed from their patch; their contents are not fetched (less context, findings may not anchor).
  - Bitbucket Server: files beyond the limit are **skipped** (`file_limit`), because the patch is built from the contents. (Part B changes this sentence.)
  - Every file within the limit costs two content requests to the provider.
- `README.md` "Local or slow model" bullet list: one bullet pointing at the new section for pull requests with many files.
- `docs/troubleshooting.md`: the `file_limit` rows quote the new note.
- `CHANGELOG.md` under `## [Unreleased]`: "Changed: `diff.max_files_full_content` defaults to 300 (was 50)." and "Added: a note naming `diff.max_files_full_content` when it skipped files; the `diff.*` keys are documented in Setup."

- Q1: `server_info` shows `diff.max_files_full_content: 300 (default)`.
- Q2: a Bitbucket Server pull request with more than 50 changed files: no `file_limit` skips; with `review.max_chunks` high enough, no Omitted files.
- Q3: the same pull request with `REVIEW_MCP_DIFF_MAX_FILES_FULL_CONTENT=10`: the note names the key and the right count; no generic provider note.

## Part B — X-44: Bitbucket Server native diff beyond the file limit

### B.0 Entry criteria (WP-14b does not write production code before these are closed in its report)
- **E1 — endpoint.** Confirm from Atlassian's REST documentation for Bitbucket Data Center 7.0 and the current major, and record in the report with links:
  - the endpoint that returns the diff of one path **between two commits** (expected: `GET /rest/api/1.0/projects/{projectKey}/repos/{repositorySlug}/diff/{path}?since={base}&until={head}&contextLines=3&whitespace=` …); the pull-request diff endpoint is **not** used, because it follows the pull request's moving refs instead of the pinned SHAs;
  - how a rename is requested (`srcPath`);
  - the JSON shape: `diffs[].source/destination`, `hunks[].sourceLine/sourceSpan/destinationLine/destinationSpan`, `segments[].type` (`ADDED`, `REMOVED`, `CONTEXT`), `lines[].source/destination/line`, and every `truncated` flag (line, segment, hunk, diff, response);
  - how binary files are reported;
  - the server-side limits that set `truncated` (diff lines, line length) and whether they can be read from the API.
  If any point cannot be confirmed from documentation, it is a DESIGN-QUESTION, and the fixture records the assumption.
- **E2 — known defect.** BSERV-12035 (truncated JSON on the pull-request diff endpoint) is fixed in 7.0, the minimum version (DQ-20). A response that does not parse as JSON is `fetch_failed`, never a partial patch.

### B.1 Behaviour (X-44)
1. Files are classified in API order as today. The first `diff.max_files_full_content` files that pass the filter keep the content path (DQ-19). Their patches do not change.
2. Every further file that passes the filter is fetched from the native diff endpoint at `pr.BaseSHA` → `pr.HeadSHA`, with `contextLines=3`, through the same bounded concurrency (`provider.ContentFetchConcurrency`), the same client, auth, redirect guard and size guards.
3. The JSON is converted to a hunk-only unified diff in the exact format of the local diff (same hunk headers, same `\ No newline at end of file` handling as far as the JSON allows; E1 records what it carries).
4. The file is listed with `BaseStatus`/`HeadStatus = not_fetched_file_limit` (added: base `not_applicable`; deleted: head `not_applicable`), like Gitea, GitHub and GitLab.
5. Outcomes:
   - any `truncated: true` at any level for that file → skipped `size_limit` (never a partial patch);
   - binary → skipped `binary`;
   - no hunks (pure rename, mode change) → skipped `empty_diff`, as today;
   - HTTP or parse failure → skipped `fetch_failed`; the run goes on;
   - `diff.max_diff_bytes` counts native diff bytes too; once exceeded, the remaining files are skipped `size_limit`, as for the content path.
6. `file_limit` is no longer produced by Bitbucket Server. The reason stays defined (other code and old records may hold it).
7. Logs: counts per outcome only (debug). Never a path list, a patch or a response body (X-8).
8. Inline anchoring: files beyond the limit have no head content, so suggestions on them use the existing `head_unavailable` path; findings that cannot anchor stay in the overview, as on the other providers.

### B.2 WP-14b (Opus, 3 commits)
1. `feat(bitbucketserver): read native diffs between two commits` — the client call, the JSON types, the converter, unit tests on recorded synthetic JSON (added, modified, deleted, renamed with `srcPath`, no trailing newline, binary, each `truncated` level, malformed JSON).
2. `feat(bitbucketserver): review files beyond the file limit from native diffs` — the `GetDiff` change (B.1).
3. `test(contract): files beyond the file limit keep their patch` — the contract case `fileLimit/beyond_cap` requires, for **every** provider, that the file is listed with its patch and `not_fetched_file_limit` (no skip). The fixture server of the Bitbucket contract harness serves the native diff endpoint.

Canaries (each proven on the reported commit, mutation + failure line + tree hash):
- **[canary] equivalence:** for every file of the shared contract fixtures, the converter's patch from the fixture JSON equals the locally generated patch of the same contents, byte for byte. Mutation: drop the context lines of a hunk.
- **[canary] pinned commits:** the request carries `since=<BaseSHA>` and `until=<HeadSHA>`. Mutation: omit `since`.
- **[canary] truncation:** a `truncated` flag at the hunk level skips the file as `size_limit`. Mutation: ignore hunk-level `truncated`.
- **[canary] no file_limit:** a 120-file synthetic pull request with the limit at 50: 120 files listed, 0 `file_limit`. Mutation: restore the old `case len(tasks) >= p.maxFiles` skip.
- **[canary] within-limit unchanged:** the patches of the first 50 files are byte-identical to the 2.5.1 (Part A) output (golden). Mutation: route file 1 through the native path.
- Secrets: the existing Bitbucket token-leak tests cover the new call (assert it).

## Rules (both parts, unchanged)
- One commit per item, in order, messages as written; `Co-Authored-By` and `Claude-Session` trailers.
- Each commit gated alone in a detached-HEAD worktree (`golang:1.26.0`, golangci-lint v2.14.0, `go test -race ./...`); Windows CI checked before each report. The gate script stays outside the worktrees, read-only, and its SHA-256 is in each report.
- Canaries proven one at a time on the reported commit's own tree (`git rev-parse <commit>^{tree}`), with mutation, failure line and tree hash before/after.
- Output schemas validated against the declared schemas in tests (the WP-10d rule).
- A missing decision is a DESIGN-QUESTION with a recommendation, never a silent choice.
- Clean-room: synthetic fixtures, placeholder hosts only (`bitbucket.example.com`).
- Never merge, tag or publish.
