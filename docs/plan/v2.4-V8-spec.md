## 0. Decisions

- **X-43 — Repository tools.** With repository context on (X-22) and tool rounds allowed, `pr_review` and `pr_ask` let the model ask, through the endpoint's tool calling, for reads inside the fetched head commit of the pull request:
  - a file or a line range of it;
  - a directory listing;
  - a fixed-string search.

  The rules:
  - Reads run in the server, on the commit that X-22 already fetched, with the X-22 offline isolation (no network, no lazy fetch, no hooks, no repository configuration as code).
  - Paths are confined to the repository.
  - Every result is budgeted, fenced as untrusted data and accounted for in the result.
  - Nothing is built, run or loaded as code (R-1).
  - An endpoint that does not accept tools gets today's single-pass call and a note, never an error.

**Owner defaults (approved 2026-10-18):**
1. **Opt-in.** Operator key `context.repo.max_tool_rounds` (default **0** = off; range 0–6). It needs `context.repo.enabled` (stdio only, as X-22). A repository file cannot turn it on or raise it (not in the X-40 allow-list).
2. **Three tools, head commit only:**
   - `read_file(path, start_line?, end_line?)`;
   - `list_dir(path)`;
   - `search(text, path?)`, which runs `git grep -F` on the head commit.

   The base is never fetched for this (X-22 rule).
3. **Budgets:**
   - `context.repo.max_tool_tokens` (default 6,000; range 500–40,000) for all tool output of one call together;
   - each tool result capped at 2,000 tokens, cut at a line boundary with a marker;
   - at most 4 tool calls per round.
   - The loop never trims the diff: each request must fit the context window with the diff whole. Before a round would not fit, the loop stops and asks for the answer.
4. **Scope:** `pr_review` (one-call reviews, full and incremental) and `pr_ask`.
   - A review in parts uses no tools, with a note (backlog).
   - Focused runs may use tools; the merged publish (`findings`) makes no model call.
   - `pr_describe` and `pr_improve`: backlog.
5. **Capability:**
   - No probe. The first request of a process to an endpoint and model carries the tools.
   - If the endpoint refuses them, or the answer shows the model ignores them, the run continues single-pass with a note, and the process remembers "no tools" for that endpoint and model.
   - A fallback model (X-38) is treated the same way.
6. **Rate limits:** every round is one model call through the X-37 limiter and counts in `llm_calls`. With a gateway limit, a review with tools takes more time; the docs say so plainly.
7. **Deterministic secret-pattern scanning** (named in the design note): not in V-8; backlog. V-8 is the read-only view and the loop.
8. **Version:** `2.4.0-rc.1`.

## 1. WP-12a — Tool calling in the LLM client (Opus)

1. **Wire types:**
   - `chatRequest` gets `Tools []tool` (`type: "function"`, `function: {name, description, parameters}` as JSON Schema) and `ToolChoice` (`"auto"` or `"none"`), both omitted when empty.
   - `message` gets `ToolCalls []toolCall` (assistant) and `ToolCallID` (tool role); `Content` may be empty on an assistant message with tool calls.
   - `chatResponse` reads `choices[].message.tool_calls` (`id`, `type`, `function.name`, `function.arguments` as a JSON string) and `finish_reason`.
2. **API:** a new method next to `Complete`, without changing it:

   ```
   Converse(ctx, Conversation) (Turn, error)
   ```

   - `Conversation` holds the system text, the ordered messages, the tools and the tool choice.
   - `Turn` holds the text, the tool calls, `Truncated` and `Usage`.
   - `Complete` stays the single-pass path, byte-identical on the wire.
3. **Same wrapping:** `Converse` goes through the same retry, rate limiter (X-37) and fallback chain (X-38) as `Complete`. The chain stays sticky per run: a conversation never changes model in the middle. If the primary fails before the first turn, the run starts on the fallback. If it fails later, the conversation is retried once from its start on the fallback, or the run ends single-pass with a note.
4. **"No tools" detection,** remembered per process for endpoint (X-37 key) and model, never logged with content:
   - HTTP 400/422 whose body mentions `tool` or `function` (the body is matched in memory, never logged);
   - or an answer with `finish_reason` `tool_calls` but no parsable calls.

   A model that simply answers without calling tools is not "no tools"; that run's tool status is `not_used`.

   The run continues with `Complete` and the note "The LLM endpoint does not accept tool calls, so the review used the diff and repository context without reading further files."
5. **Arguments:** tool-call arguments are parsed as JSON, at most 4 KiB each. Invalid JSON gets a tool result "invalid arguments" without running anything.
6. **Tests:**
   - a fake endpoint answering with tool calls, with a refusal (400 with "tools"), and with garbage calls;
   - limiter and fallback interplay (a 429 mid-conversation waits; the fallback restarts the conversation);
   - `Complete` unchanged on the wire (golden request).

   **Canary:** treat a 400 with "tools" as a hard error, and the refusal test fails.

Commits:
1. `feat(llm): add tool calling to the client`
2. `feat(llm): remember endpoints that refuse tools`

## 2. WP-12b — Repository tools and the loop in `pr_review` (Opus)

### 2.1 Tools

New package `internal/repotools`, on `repoctx.Session` and `gitctx`, offline only.

| Tool | Parameters | Behaviour |
|---|---|---|
| `read_file` | `path` (string), `start_line`, `end_line` (optional, 1-based) | The file at the head SHA, numbered like the diff. At most 400 lines per call; without a range, the first 400. Binary files, files the partial clone lacks (over 1 MiB) and files over `diff.max_file_bytes` give a fixed result ("not available: binary / not fetched / too large"), never a fetch. |
| `list_dir` | `path` (string, `""` for the root) | Entries of the directory at the head SHA, directories with a trailing `/`, at most 200, then "and N more". |
| `search` | `text` (2–200 characters), `path` (optional directory prefix) | `git grep -n -F -I` at the head SHA, at most 50 hits with 1 context line, the RC-7 limits and timeouts. |

**Path rules** (one function, used by every tool; tested as a table):
- relative, cleaned, `/`-separated, at most 4,096 bytes, no control characters;
- no `..` segment, no leading `/`, no `\`, no empty segment, no `.git` segment;
- resolved only as `<head sha>:<path>` through git, never against the file system.
- A refused path gives the result "path not allowed" without a git call.

**Results:**
- Fenced as untrusted data under a fixed header naming the tool, the path and the line range.
- Cut to 2,000 tokens at a line boundary with a marker.
- Counted against `context.repo.max_tool_tokens`. A call over the remaining budget gets "budget exhausted" and the loop ends.

### 2.2 The loop

1. When it runs: `max_tool_rounds` > 0, the repository context is `used`, the review is one call, and the endpoint is not marked "no tools". Otherwise the run is single-pass as today; the reason is in `coverage.repo_context.tools.reason`: `off`, `repo_context_unavailable`, `review_in_parts`, `endpoint_no_tools`.
2. The system prompt gets one fixed instruction block (absent otherwise). It tells the model:
   - the tools read the pull request's head commit;
   - use them only when the diff and the repository context are not enough to judge a finding;
   - at most N rounds;
   - the final answer is the usual YAML, with no tool call in it.
3. **Rounds:** each round is a `Converse` call with `tool_choice: auto`. The tool calls of an answer (at most 4; extra ones get "too many calls in one round") run in order, their results are appended, and the next round follows. After `max_tool_rounds` rounds, or when the budget is exhausted or the next request would not fit, one last call with `tool_choice: none` asks for the answer.
4. **Parsing:** the final text goes through the existing YAML parsing and re-ask (`callPart`). A re-ask is a plain `Complete` with the conversation's final user turn and the re-ask note; it does not count as a round.
5. **The diff wins:** before each round the full request is measured. If it would not fit with the diff whole, no further tool round is made.
6. **Incremental runs** (X-36): tools read the head commit like a full run; the changed-files scope is unchanged.

### 2.3 Output and logs

1. `coverage.repo_context.tools`, always present in `pr_review` and `pr_ask`:

   ```
   {status, reason, rounds, calls: [{tool, target, status, tokens}], tokens}
   ```

   - `status`: `used`, `not_used` (allowed but the model made no call), `off`, `skipped`.
   - `target`: the path or the search text, cut to 200 characters, control characters removed.
   - Call `status`: `ok`, `not_allowed`, `not_available`, `too_large`, `budget_exhausted`, `invalid_arguments`, `too_many_calls`.
   - The coverage schemas declare it with `additionalProperties: false`.
2. Metadata: `tool_rounds` (int).
3. Notes (fixed sentences):
   - the no-tools note (§1 item 4);
   - "The review was made in parts, so repository tools were not used.";
   - "The repository tool budget was used up after N calls."
4. **Logs:** tool name, status, token count and round, never file content, search text or paths beyond the repository-relative path at debug level.

### 2.4 Tests and canaries

- the path table (each refusal, no git call);
- each tool on a fixture repository (offline, a partial-clone blob missing, a binary, a large file);
- the loop on a fake endpoint (two rounds then answer; budget exhausted; the round limit with `tool_choice: none`; the diff never trimmed across a sweep of context windows; a refusing endpoint gives single-pass and the note);
- the fence holds tool output containing the fence string and "ignore previous instructions";
- no network during tool calls (`protocol.allow=never` asserted);
- every new result case validated against the declared schema.

**Canaries:**
1. Accept a `..` segment → the path test fails.
2. Let a round go out with the diff trimmed → the sweep test fails.
3. Run a fourth-plus-one call in a round → the per-round test fails.

1. `feat(repotools): read files, list directories and search the head commit`
2. `feat(review): let the model read the repository through tools`
3. `feat(review): report repository tool use`

## 3. WP-12c — `pr_ask`, `server_info`, docs, acceptance (Sonnet)

1. **`pr_ask`:** the same loop and output; its final answer is free text (no YAML), so the last call needs no re-ask.
2. **`server_info`:** reports `context.repo.max_tool_rounds` and `max_tool_tokens`, and, per endpoint and model seen by this process, "tools: not known yet / accepted / refused".
3. **Docs:**
   - `docs/repo-context.md` "Repository tools": what the model can read, the limits, the budgets, the no-tools fallback, the rate-limit cost, what is never done;
   - `docs/setup.md` keys;
   - `docs/troubleshooting.md` every note and call status;
   - decisions doc X-43 with every settled DQ;
   - CHANGELOG `## [Unreleased]` planned as `2.4.0-rc.1`.
4. **Acceptance (owner, after the release; stdio, repository context on):**
   - **Q1:** a throwaway PR whose diff calls a function defined in an unchanged file with a subtle contract (for example, it returns `nil, nil` for "not found"). `max_tool_rounds` 3 → `tools.status` `used`, a `read_file` of that file in `calls`, and a finding that depends on it.
   - **Q2:** the same with `max_tool_rounds` 0 → `off`, single pass.
   - **Q3:** a path the model is told to read outside the repository (fixture: the PR description asks for `../../etc/passwd`) → `not_allowed`, nothing read.
   - **Q4:** `max_tool_tokens` 500 → `budget_exhausted` and the note.
   - **Q5:** an endpoint or model without tool calling (owner's choice, or a fake endpoint answering 400 "tools not supported") → single pass and the no-tools note; a second call in the same process makes no tool request.
   - **Q6:** `pr_ask` with tools ("Where is X defined and what does it return?").

Commits:
1. `feat(ask): let the model read the repository through tools`
2. `feat(tools): report repository tools in server_info`
3. `docs: document repository tools`
