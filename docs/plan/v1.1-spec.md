## 0. Decisions (added to the decisions doc in the package that implements them)

- **X-19 — Chunked review (RC-11…RC-14).** When the prepared diff does not hold every reviewable file, `pr_review` reviews the rest in further model calls ("chunks"), up to `review.max_chunks` calls in total, and merges the results. `review.max_chunks = 1` is the v1.0 behaviour.
- **X-20 — Deletions listed by name are not budget losses.** A deleted file whose patch is dropped by design (the ported deletion handling) and whose name is in the prompt's deleted-files list counts as **reviewed**: its deletion was shown to the model. Only deletions cut by the budget are "not reviewed". This settles 9a DESIGN-QUESTION 1.
- **X-21 — `pr_ask` does not chunk in v1.1 (RC-15).** Merging several answers needs a further reduce call and its own honesty rules; that is backlog. Instead, files the question names are admitted first, and the X-18 banner stays.
- **X-22 — Repository context (RC-1…RC-10).** As in the design note, with the open questions settled in §3.0.
- **X-23 — `pr_info`: target branch, reviewers and approvals (Track C, added 2026-10-08, owner request).** A read-only tool, no LLM call, that answers "what does this pull request merge into" and "who has really reviewed or approved it". Human reviewers are separated from review-mcp's own activity (the token user's marked overview, inline findings and AI reviews), so an AI review never reads as an approval.
- **Confirmed from 9a:** binary and empty-diff files stay outside `total_files` (9a DESIGN-QUESTION 2).

## 2. Track A — Chunked review

### WP-11e1 — Deletion accounting and chunk packing (diffpipe)

1. **Split deletions (X-20).**
   - `Prepared` gains `DeletedListed []string`: deleted files dropped by the deletion handling **whose names are in `Text`'s deleted-files section**.
   - `Omitted.Deleted` keeps only deletions whose names are not in `Text` (cut by the budget, or the section did not fit).
   - The accounting invariant gains `len(DeletedListed)` on the left side. Update the invariant comment and its test.
   - `Coverage.Tally()` counts `DeletedListed` as reviewed. Coverage lists them under a new heading "Deleted (listed by name)". The structured `coverage` gains `deleted_listed` (array of paths), in every schema that carries `coverage`.
2. **`PrepareChunks`.** A new function in `diffpipe`:
   ```go
   // PrepareChunks splits the reviewable files into at most maxChunks
   // prepared diffs. Chunk 1 is exactly Prepare(in). Every further chunk
   // is Prepare over the files earlier chunks did not include, clip or
   // list, in the original rank order.
   func PrepareChunks(in Input, maxChunks int) (*Chunks, error)
   ```
   - `Chunks` holds `Parts []*Prepared` and the overall accounting: `Included`, `Clipped`, `DeletedListed`, `Omitted` (files left after the last chunk), `Skipped`, `TooLarge`.
   - Chunk 1 is byte-identical to `Prepare(in)`. A golden asserts it for every existing diffpipe fixture.
   - Each further chunk receives the remaining `provider.FilePatch` entries and **no** provider skips (those are accounted once, from chunk 1).
   - The deleted-files section appears only in the chunk where those names fit; a name is listed in at most one chunk.
   - **A file larger than a whole chunk:** when a further chunk admits nothing, `large_patch_policy` applies to its top file as today. With `clip`, the clipped file is that chunk's content. With `skip`, the file is recorded under a new skip reason `too_large` and packing continues with the next file; it never ends the packing. `too_large` counts as **not reviewed** in `Tally()`.
   - `ErrDoesNotFit` is returned only when chunk 1 itself does not fit (today's behaviour). Later chunks never return it.
   - Packing stops when no reviewable file remains or `maxChunks` parts exist. Files still left are `Omitted` (budget), exactly as today.
3. **Invariant for chunks.** Every input file appears exactly once across: the union of the parts' `Included`, `Clipped`, `DeletedListed`; `TooLarge`; the final `Omitted`; `Skipped`. Property test over the randomized generator already used by the oracle tests (at least 500 cases, fixed seed).
4. **Tests.**
   - Goldens: a PR that needs 3 chunks; one where the 2nd chunk is a clipped single file; one with `skip` and a too-large file in the middle; one that hits `maxChunks`.
   - `maxChunks = 1` equals `Prepare` for every fixture.
   - **[canary]** Count `DeletedListed` as not reviewed: the accounting test fails.
   - **[canary]** Give chunk 2 the provider skips again: the invariant test fails (double count).
   - **[canary]** Let a file appear in two chunks (skip the "already taken" filter): the property test fails.

Commit: `feat(diffpipe): account listed deletions as reviewed and pack remaining files into chunks`

### WP-11e2 — Chunked pipeline, merge and honesty

1. **Pipeline.**
   - `review.Run` uses `PrepareChunks(in, args.MaxChunks)` instead of `Prepare`. With one part, behaviour, prompts and goldens are unchanged.
   - Each part is one model call with the same scaffolding: the system prompt, the PR title and description, the discussion block (each call gets its own budget, as today) and the part's diff.
   - **Part header.** When there is more than one part, the user template gets one line before the diff:
     > "This pull request is large and is reviewed in N parts. This is part I of N. Review only the files in the diff below; the other files are reviewed separately."

     Record the deviation in the template header, like the earlier ones.
   - Calls run **sequentially** (local endpoints are usually single-slot; parallel calls would only queue). Progress reports `calling model (part I of N)`.
   - Each call has its own `llm.timeout_seconds`. The YAML repair and the re-ask work per part, unchanged.
2. **Merge (RC-12).**
   - `key_issues_to_review`: the parts' findings in part order, then model order; fingerprint dedup (X-13) across parts and against existing threads; then capped at `review.max_total_findings`. Each part still asks for at most `review.max_findings`.
   - Findings dropped by the total cap add the note "N further findings were not shown because of review.max_total_findings." They are **not** silently lost.
   - `estimated_effort_to_review`: the maximum of the parts that returned one.
   - `relevant_tests`: true if any part says true; false if every part that answered says false; nil if none answered.
   - `security_concerns` and `performance_concerns`: "No" when every part says "No"; otherwise the non-"No" texts joined by a blank line, each prefixed with `Part I:` only when more than one part has a concern.
   - Snippet verification, links and inline anchoring run on the merged list, against the full PR file set, unchanged.
3. **Failure of a part.**
   - A part whose call fails (timeout, LLM error, unparseable output after repair and re-ask): its files become **not reviewed** with reason `model_call_failed`, and the note "Part I of N failed (<fixed error class>); its files were not reviewed." Never the raw error text.
   - If **every** part fails, the run returns the first part's classified error, as today.
   - If part 1 succeeds and a later part fails, the result is partial (X-18 banner) and publishable.
4. **Honesty (RC-13).**
   - Coverage counts all parts. The structured `coverage` gains `model_calls` (int) and `failed_parts` (int).
   - Client and provider renderings add "Reviewed in N model calls." to the coverage section when N > 1.
   - Files left after `max_chunks` stay "not reviewed" with the X-18 banner. The partial hint gains: "raise review.max_chunks" whenever `max_chunks` was reached. Keep the 9a rule: mention `diff.max_tokens` only when it was the limit that applied.
5. **Time (RC-14).**
   - stdio: unchanged mechanics. A chunked review is simply a longer call; X-16 turns it into a background job.
   - serve: synchronous. `docs/serve.md` tells serve clients to raise their tool timeout for large PRs, or to set `review.max_chunks = 1`.
6. **`pr_ask` (X-21).**
   - `pr_ask` keeps one call.
   - Files the question names are admitted first: a changed file is pinned when its full path, or its base name of at least 5 characters, occurs in the question (case-sensitive, whole token). Pinned files keep their relative order and go before the ranked rest; pinning never overrides filters.
   - Coverage and the banner are unchanged.
7. **Docs.**
   - `docs/review.md`: "Large pull requests" (parts, `max_chunks`, `max_total_findings`, sequential calls, what a failed part means, time per part).
   - `docs/ask.md`: question-named files go first; `pr_ask` does not use parts.
   - Troubleshooting: "The review took several minutes" and "Part I of N failed".
   - README local-model example: mention that `REVIEW_MCP_DIFF_MAX_TOKENS` now makes each part smaller, not the review shorter.
   - X-19, X-20, X-21 in the decisions doc. `CHANGELOG.md` `1.1.0-rc.1` section (Unreleased until tagged).
8. **Tests.**
   - A fake LLM that answers per part from fixtures: 3 parts merged; dedup across parts; the total cap and its note; effort, tests and concerns merging; a part failing in the middle; every part failing.
   - `max_chunks = 1` reproduces every existing review golden byte for byte.
   - Through the MCP server (stdio): a 3-part review as a background job, with progress messages and the final result through `job_result`; publish posts one overview and one Gitea review.
   - `pr_ask` pinning: a named file that would be omitted by the budget is included.
   - **[canary]** Drop the dedup: the duplicate test fails.
   - **[canary]** Treat a failed part's files as reviewed: the honesty test fails.
   - **[canary]** Apply `max_findings` to the merged list instead of `max_total_findings`: the cap test fails.

Commit: `feat(review): review large pull requests in parts and merge the results`

## 3. Track B — Repository context

### 3.0 Open questions, settled
1. **Bitbucket Server git auth.** First `Authorization: Bearer <token>`. On an HTTP 401 from `git`, retry once with HTTP Basic, user name from the token identity (P7 `X-AUSERNAME`), password the token, sent the same way (environment `http.extraHeader`, never a URL). The scheme that worked is cached for the process. Both are tested hermetically; 11d records which one works live.
2. **Gitea git auth.** First `Authorization: token <token>`. On 401, retry once with Basic, user name from `GET /api/v1/user` (P7), password the token. Same caching and live recording.
3. **Windows.** `core.hooksPath=NUL`. Locks use `O_CREATE|O_EXCL` on a `.lock` file, which behaves the same on Windows. CI adds the `internal/gitctx` tests on `windows-latest`; tests that need `git http-backend` are skipped there with a stated reason.
4. **No `git` on the machine.** It is a note, never an error (RC-2). `server_info` shows `context.repo` as `enabled, git <version>` or `enabled, unavailable: <fixed reason>`.

### WP-11a — git runner and cache (Opus)
As design note §3 11a, plus:
- `internal/gitctx` has no dependency on `internal/review`. Its API: `Ensure(ctx, Repo, PR) (Checkout, error)` and `Grep(ctx, Checkout, Query) ([]Hit, error)`. 11b adds `Grep`; 11a stubs it.
- Every child process gets a fresh environment built from an allowlist (`PATH`, `SYSTEMROOT` on Windows, `LANG=C`, the proxy variables `http_proxy`/`https_proxy`/`no_proxy`/`all_proxy` in either case when set) plus the git config variables. Never the parent's full environment: it may hold other tokens.
- **Isolation from the user's git configuration (architect, 11a review):** `HOME`, `XDG_CONFIG_HOME` (and `USERPROFILE` on Windows) point at an empty `<cache_dir>/.home` (0700); `GIT_CONFIG_NOSYSTEM=1` everywhere except Windows. Before any network call, `git ls-remote --get-url origin` must print exactly the pinned clone URL, else reason `redirect` and nothing is sent.
- **TLS mirrors the provider client:** `ca_cert` → `-c http.sslCAInfo=<path>` (plus `-c http.sslBackend=openssl` on Windows); `insecure_skip_verify` → `-c http.sslVerify=false`.
- **Cache layout:** `host[_port]/<escaped base path or _>/namespace/repo`, so two instances on one host never share an entry.
- **Reads are offline:** every `git grep`, `cat-file`, `rev-list`, `ls-tree` runs without credentials, with `protocol.allow=never` only and `GIT_NO_LAZY_FETCH=1`; a blob that was not fetched is counted as skipped, never fetched.
- Error and debug text from `git` stderr is never passed on. It is mapped to fixed reasons (`auth`, `not_found`, `timeout`, `too_large`, `sha_mismatch`, `redirect`, `git_failed`).
- `diag cache [--prune]`.
- Canaries as in the design note (token on disk, token in argv, SHA mismatch), plus **[canary] parent environment:** set a sentinel variable in the parent; the child's environment (captured by the fake `git`) must not contain it.

Commit: `feat(gitctx): fetch pull-request heads into a credential-safe, self-pruning cache`

## 4. Track C — Pull-request status

### WP-11f — `pr_info` (Sonnet; branch `v11-pr-info` from `v11-chunked`, own draft PR; independent of Track B)

1. **Tool `pr_info`** (stdio and serve; read-only; needs only a read token).
   - Input: `pr_url`.
   - Output (structured and markdown, client profile):
     - `title`, `author`, `state` (`open`, `merged`, `closed`; plus `draft: bool` where the provider has it), `web_url`;
     - `source_branch`, `target_branch`, `head_sha`, `merge_base_sha` with `base_strategy` (already resolved by the providers);
     - `reviewers`: one entry per human reviewer: `user` (login and display name), `requested` (bool), `state` (`approved`, `changes_requested`, `commented`, `pending`), `stale` (bool: the state was given on an older commit than the head, where the provider reports it), `at` (time, when known);
     - `approvals`: `{approved: N, changes_requested: N, pending: N}` counted over `reviewers`;
     - `required_approvals`: an int when the provider exposes it to this token, otherwise `null` with `required_approvals_note` "not readable with this token" (never a guess);
     - `mergeable`: `true`, `false` or `null` (unknown), with `merge_blockers`: fixed short reasons only where the provider gives structured ones;
     - `review_mcp_activity`: `{overview: bool, inline_findings: N}` for the token user's marked comments (X-12, X-13 markers plus author check).
   - Text rendering: a short block, target branch first ("`feature/x` → `main`"), then the approval line ("2 of 2 required approvals; 1 changes requested"), then one line per reviewer.
2. **Gitea.**
   - PR: `GET /repos/{o}/{r}/pulls/{n}` (`base.ref`, `head.ref`, `draft` when present, `requested_reviewers`, `mergeable`).
   - Reviews: `GET /repos/{o}/{r}/pulls/{n}/reviews` (paged). Per user, the latest non-dismissed review with state `APPROVED` or `REQUEST_CHANGES` decides; `COMMENT` only counts when there is no decisive one; `PENDING` reviews of other users are not visible and are not reported. `stale` from the review's `stale` field; `official` is kept in debug logs only.
   - Required approvals: `GET /repos/{o}/{r}/branch_protections/{target}` → `required_approvals` when the call succeeds; a 403/404 gives `null` plus the note.
   - Reviews by the token user that carry review-mcp's markers (or whose body is review-mcp's inline batch) are **not** reviewers; they are `review_mcp_activity`. A plain human review by the same account (no marker) is a reviewer.
3. **Bitbucket Server / Data Center.**
   - PR: `GET .../pull-requests/{id}` (`fromRef`, `toRef.displayId`, `draft` when present, `reviewers[]` with `status` `APPROVED`/`NEEDS_WORK`/`UNAPPROVED`, `lastReviewedCommit`).
   - `stale`: `lastReviewedCommit` present and different from the head SHA.
   - Merge status: `GET .../pull-requests/{id}/merge` → `canMerge`, `vetoes[].summaryMessage` mapped to `merge_blockers` as fixed text where the summary is one of the known vetoes (required approvers, needs work, required builds, merge conflict); unknown vetoes become "other merge check" (never raw server text). Required approvals are taken from the veto when it states a number; otherwise `null` plus the note.
   - Participants who are not reviewers are not listed (only `reviewers[]`).
4. **Honesty and errors.**
   - Any sub-call that fails (reviews, protection, merge status) gives `null` fields plus a note; the tool never fails as a whole because an optional part is unreadable. The PR call itself failing uses the existing provider error sentences.
   - Comment and review bodies are never read into the output (only states and markers).
   - Display names pass through the existing sanitizer for client markdown.
5. **Docs.** `docs/pr-info.md` (fields, per-provider sources, required scopes, why AI reviews are excluded), README tool table row, setup token checklist (Gitea: `read:repository`, `read:issue`, `read:user`; protection read may need repository admin and is optional), X-23 in the decisions doc, CHANGELOG `1.1.0-rc.1`.
6. **Tests.** Fixtures per provider: approved, changes requested, stale approval, requested-but-silent reviewer, dismissed review, the token user's marked AI review excluded, a human review from the same account included, protection 403 → `null` plus note, Bitbucket vetoes known and unknown. Through the MCP server: tool listed in stdio and serve with an output schema; serve with header credentials.
   - **[canary]** count review-mcp's own marked review as a reviewer: the exclusion test fails.
   - **[canary]** let a dismissed approval count: the Gitea state test fails.
   - **[canary]** pass a raw veto message through: the Bitbucket blocker test fails.

Commit: `feat(tools): add pr_info with target branch, reviewers and approval status`

## 5. Live acceptance (v1.1, recorded on a new "v1.1.0 acceptance record" issue)
Same rules as `v1-acceptance.md` §0: personal instances, redaction, pass or fail or not run.
- **K1** The 62-file class of PR (or any PR that needed more than 3 parts on your model): every reviewable file is reviewed (`partial: false`), or the banner names what is left and why. Record the parts, the total time and the model.
- **K2** Same PR with `review.max_chunks = 2`: the banner appears and the hint names `review.max_chunks`.
- **K3** Stop the LLM endpoint during part 2: the result is partial with the failed-part note; no raw error text.
- **K4** Publish the chunked review: one overview, inline comments from several parts, no duplicates on a second run.
- **K5** `pr_ask` naming a file that the budget would omit: the answer uses that file.
- **L1** A PR that changes a function signature with callers elsewhere: with `context.repo.enabled`, the review mentions an affected caller; with it off, record whether it does.
- **L2** Record the git auth scheme that worked on each provider (§3.0).
- **L3** Grep the cache directory for the token: no hits. Simulate idle expiry by back-dating the marker: the next use sweeps it.
- **L4** serve with `context.repo.enabled`: refuses to start with the fixed sentence.
- **L5** `tools/evalrepo` on at least 5 PRs; the 20-PR decision for stage 2 is recorded later.
- **M1** `pr_info` on a Gitea and a Bitbucket PR: the target branch matches the UI.
- **M2** One reviewer approves, another requests changes, a third is requested and silent: states and counts match the UI. Push a new commit: the approval is shown as stale where the provider reports it.
- **M3** After a `pr_review` publish on the same PR: the AI review is under `review_mcp_activity`, not under `reviewers`, and the approval count is unchanged.
- **M4** With a read-only token: `required_approvals` is a number or `null` with the note, never a guess; record which one each provider gives.
- **M5** In an MCP client: "Which branch does this PR target, and who has approved it?" is answered from `pr_info`.
